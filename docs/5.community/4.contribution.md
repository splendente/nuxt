Nuxt エコシステムに貢献できるさまざまな方法があります。

## エコシステム

Nuxt エコシステムには多くの異なるプロジェクトと組織が含まれています：

* [nuxt/](https://github.com/nuxt) - Nuxt フレームワーク自体のコアリポジトリ。[**nuxt/nuxt**](https://github.com/nuxt/nuxt) には Nuxt フレームワーク（バージョン 2 と 3 の両方）が含まれています。
* [nuxt-modules/](https://github.com/nuxt-modules) - コミュニティが貢献し、維持しているモジュールとライブラリ。モジュールを `nuxt-modules` に移行する[プロセス](/docs/guide/going-further/modules/#joining-nuxt-modules-and-nuxtjs)があります。これらのモジュールには個別のメンテナーがいますが、単一の人物に依存していません。
* [unjs/](https://github.com/unjs) - これらのライブラリの多くは Nuxt エコシステム全体で使用されています。これらはフレームワークや環境に依存しないユニバーサルライブラリとして設計されています。他のフレームワークやプロジェクトからの貢献と使用を歓迎しています。

## 貢献の方法

### Issue のトリアージとディスカッションでのサポート

サポートしたいプロジェクトの issue やディスカッションをチェックしてください。例えば、こちらは Nuxt の [issues ボード](https://github.com/nuxt/nuxt/issues)と[ディスカッション](https://github.com/nuxt/nuxt/discussions)です。他のユーザーをサポートしたり、回避策を共有したり、再現を作成したり、バグを少し調べて知見を共有したりすることは大きな違いをもたらします。

### Issue の作成

Issue を作成するために時間をかけていただき、ありがとうございます！❤️

* **バグ報告**: Issue を開く前に行うべきことについては[ガイド](/docs/community/reporting-bugs)をご覧ください。

* **機能リクエスト**: 考えている機能の範囲をカバーする既存の issue やディスカッションがないことを確認してください。機能が Nuxt エコシステムの他の部分（モジュールなど）に関するものである場合は、まずそちらで機能リクエストを提起することを検討してください。考えている機能が一般的であるか、API が完全に明確でない場合は、まず **Ideas** セクションでディスカッションを開いてコミュニティと話し合うことを検討してください。

Issue に対応する際の[内部 issue 意思決定フローチャート](https://mermaid.live/view#pako:eNqFlE1v2zAMhv8K4UuToslhx2Bo0TZt12Edhm7YMCAXWqJtorLk6qOpkfS_j7KdfpyWQ-BQr8mHL6nsCuU0FauiMm6rGvQRfq03FuRzvvvTYIQHthpcBT_ugQNwPHuZjheLxf4i1VDx8x4udrf5EBCOQvSsYg4ffS79KS9pmX9QALTgyid2KYB7Ih-4bmKWbDk2YB0E1gRUVaRi-FDmmjAmT3u4nB3DmoNKIUA1BsGSohA49jnVMQhHbDh_EZQUImyxh-gAtfaiG-KWSJ-N8nt6YtpCdgEeE5rXPOdav5YwWJIJU7zrvNADV9C7JBIyIC07Wxupkx3LFQ5vCkguRno5f9fP2qnUko0Y2dk9rGdvHAa9IIhVGlCp5FFNPN-ce4DKeXBd53xMliOLp9IZtyORQVsnrGm-WJzejtUu5fFqdr5FGQ3bLslYvGthjZbJTLpReZG5_lLYw7XQ_CbPVT92ws9gnEJj-v84dk-PiaXnmF1XGAaPsOsMKywNvYmG80ZohV8k4wDR9_N3KN_dHm5mh1lnkM5FsYzRfNiTvJoT5gnQsl6uxjqXLhkNQ9syHJ0UZZ8ERUIlNShr6N8gZDEliR-ow7QZa0fhY4LoHLRo-8N7ZxPwjRj5ZZYXpvOSNs9v3Jjs8NXB4ets92xan3zydXZHvj64lKMayh4-gZC1bjASW2ipLeWuzIuToiXfImu5rbucclMIc0ubYiWPGv3DptjYF9Fhiu5nb1Wxij7RSZE6jZHWjLXHtlhVaIJESXN0_m68_sO_wMs_oO9gyg)に従うよう最善を尽くします。

### プルリクエストの送信

プルリクエストはいつでも歓迎しています！❤️

#### 始める前に

バグを修正する前に、**それを説明する issue があるかどうか**をチェックすることをお勧めします。ドキュメントの問題である可能性や、知っておくと役立つコンテキストがある可能性があるからです。

機能に取り組んでいる場合は、まず**機能リクエスト issue を開く**ことをお願いして、メンテナーと、その機能が望まれているかどうか、およびそれらの機能の設計について話し合ってください。これによりメンテナーと貢献者の両方の時間を節約でき、機能をより早くリリースできます。プルリクエストで機能を構築する前に、issue はフレームワークチームメンバーによって**確認される必要があります**。

タイポ修正の場合は、コミット履歴をよりきれいに保つために、複数のタイポ修正を一つのプルリクエストにまとめることをお勧めします。

Nuxt 自体へのより大きな変更については、まず [Nuxt モジュールを作成](#create-a-module)してそこで機能を実装することをお勧めします。これにより迅速な概念実証が可能になります。その後、ディスカッションの形で [RFC を作成](#make-an-rfc)できます。ユーザーがそれを採用し、フィードバックを収集することで、それを洗練し、Nuxt コアに追加するか、スタンドアロンモジュールとして継続するかを決めることができます。

#### コミット規約

コミットメッセージには [Conventional Commits](https://www.conventionalcommits.org) を使用しており、これにより[コミットに基づいて自動的にチェンジログを生成](https://github.com/unjs/changelogen)できます。まだ慣れていない場合は、ガイドを通して読んでください。

`fix:` と `feat:` は**実際のコード変更**（ロジックに影響する可能性があるもの）用であることに注意してください。タイポやドキュメントの変更には、代わりに `docs:` や `chore:` を使用してください：

* ~~`fix: typo`~~ -> `docs: fix typo`

`nuxt/nuxt` のような monorepo のプロジェクトで作業している場合は、コミットの主なスコープを括弧内で指定するようにしてください。例：`feat(kit): add 'addMagicStuff' utility`。

#### プルリクエストの作成

プルリクエストの送信方法がわからない場合は、[ガイド](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-a-pull-request)を読むことをお勧めします。

プルリクエストを送信する際は、PR のタイトルも[コミット規約](#commit-conventions)に従っていることを確認してください。

PR が既存の issue を修正または解決する場合は、PR の説明でそれらについて言及してください。

1 つの PR に複数のコミットがあっても問題ありません。マージ時に `Squash and Merge` を使用してコミットを 1 つのコミットにまとめるため、変更のためにリベースや force push を行う必要はありません。

迅速なコミットを可能にするため、コミットフックは追加していません。ただし、プルリクエストを作成する前に、lint/test スクリプトが通ることを確認してください。

一般的に、PR に_関連のない_変更が含まれていないことも確認してください。例えば、編集したファイルの他の場所でエディターが空白や書式設定を変更した場合は、PR の変更内容をより明確にするためにこれらを元に戻してください。また、1 つの PR に複数の関連のない機能や修正を含めることは避けてください。分離できる場合は、複数の PR に分けてレビューとマージを個別に行う方が良いです。一般的に、PR は_一つのことだけ_を行うべきです。

#### プルリクエストを作成した後

プルリクエストを作成いただいたら、迅速にレビューするよう最善を尽くします。

メンテナーに割り当てた場合、その人がレビューに特別な注意を払い、必要な変更があれば実装します。

PR に変更を要求した場合、赤いテキストは無視してください！それが悪い PR だと思っているという意味ではありません。これは、プルリクエストのリストの状態を一目で簡単に判断する方法に過ぎません。

PR を「pending」としてマークした場合、PR のレビューで他にやるべきタスクがある可能性があることを意味します。これは内部的なメモであり、PR が良いアイデアかどうかの反映ではありません。pending 状態の理由については、コメントを通じて説明するよう最善を尽くします。

プルリクエストへの対応とレビューの際は、[PR 意思決定フローチャート](https://mermaid.live/view#pako:eNp9VE1v2kAQ_SsjXzBSEqlALlaUisSh0ACK2l4qcVm8Y9hi7672Iwly-O-ZtYPt5FAOCHbee_PmzdpVlCmOURLlhXrJ9sw4-JNuJNBnWs1UQafIQVjrERyWumAOv58-AJeXt29_0b7BXbWwwL0uRPa1vlZvcB_fF8oiMNmB2QM4BXkt3UoON7Lh3LWaDz2SVkK6QGt7DHvw0CKt5sxCKaQoWQEGtVHcZ04oGdw04LTVngW_LHOeFcURGGz97mw6PSv-iJdsi0UCA4nI7SfNwc3W3JZit3eQ1SZFDlKB15yswQ2MgbOjbYeatY3n8bcr-IWlekYYaJRcyB04I9gOB1CEfkF5dAVTzmFAtnqn4-bUYAiMMmHZgWhNPRhgus5mW2BATxq0NkIZ4Y4NbNjzE2ZchBzcHmGLe_ZMSKCcyRXyLrVFa_5n_PBK2xKy3kk9eOjULUdltk6C8kI-7NFDr8f4EVGDoqlp-wa4sJm3ltIMIuZ_mTQXJyTSkQZtunPqsKxShV9GKdkBYe1fHXjpbcjlvONlO9Kqx_M7YHmOmav_luxfE5zKwVs09hM5DLSupgYDlr5flDkwo7ykixKG-xDsUly1LZ-uY32dgDc7lG7YqwbNp0msJwmIUivjWFtfd-xRrEcJ7Omydz37qFplHOtxEp4GskI2qB5dRCWakglOz3oV8JuITJa4iRL6yZk5bKKNPBGOead-H2UWJc54vIiaW53SPgwrz4fIhVNm1bw76lfI6R2_MW21)に従うよう最善を尽くします。

### モジュールの作成

Nuxt でクールなものを作成したなら、なぜ[モジュールに抽出](/docs/guide/going-further/modules)して他の人と共有しないのでしょうか？すでに[多くの優れたモジュール](/modules)がありますが、常により多くのモジュールの余地があります。

構築中にヘルプが必要な場合は、お気軽に[ご相談ください](/docs/community/getting-help)。

### RFC の作成

大きな新機能をテストし、コミュニティの採用を得るために、まず[モジュールの作成](#create-a-module)を強くお勧めします。

すでにそれを行っているか、新しいモジュールを作成するのが適切でない場合は、新しいディスカッションを作成することから始めてください。あなたの考えをできるだけ明確に説明してください。新しい API のコード例や関数シグネチャを含めてください。既存の issue や問題点を例とともに参照してください。

これが RFC になるべきだと思った場合、カテゴリを RFC に変更し、フィードバックのためにより広く配信します。

RFC は次の段階を経て進行します：

* `rfc: active` - 現在コメント受付中
* `rfc: approved` - Nuxt チームによって承認済み
* `rfc: ready to implement` - issue が作成され、実装のために割り当てられた
* `rfc: shipped` - 実装済み
* `rfc: archived` - 承認されていないが、将来の参考のためにアーカイブ済み

### エコシステム全体の規約

以下の規約は `nuxt/` 組織内では_必須_であり、エコシステムの他のメンテナーにも推奨されます。

#### モジュール規約

モジュールは [Nuxt モジュールテンプレート](https://github.com/nuxt/starter/tree/module)に従う必要があります。詳細については[モジュールガイド](/docs/guide/going-further/modules)をご覧ください。

#### コア `unjs/` ライブラリの使用

エコシステム全体で使用されている以下のライブラリをお勧めします：

* [pathe](https://github.com/unjs/pathe) - ユニバーサルパスユーティリティ（Node `path` の置き換え）
* [ufo](https://github.com/unjs/ufo) - URL 解析と結合ユーティリティ
* [unbuild](https://github.com/unjs/unbuild) - rollup ベースのビルドシステム
* ... さらに多くのライブラリについては [unjs/](https://github.com/unjs) 組織の他のライブラリをチェックしてください！

#### ESM 構文の使用と `type: module` のデフォルト化

Nuxt エコシステムの大部分は ESM を直接消費できます。一般的に、`__dirname` や `require` ステートメントなどの CJS 固有のコードの使用を避けることを推奨します。[ESM について詳しく読む](/docs/guide/concepts/esm)ことができます。

#### Corepack とは

[Corepack](https://nodejs.org/api/corepack.html) は、対応するコマンドを実行する際にパッケージマネージャーの正しいバージョンを使用していることを確認します。プロジェクトの `package.json` に `packageManager` フィールドがある場合があります。

以下に示すような設定のプロジェクトでは、Corepack は `pnpm` の `v7.5.0`（まだ持っていない場合）をインストールし、それを使用してコマンドを実行します。

```jsonc [package.json]
{
  "packageManager": "pnpm@7.5.0"
}
```

#### ESLint の使用

[`@nuxt/eslint`](https://github.com/nuxt/eslint) で [ESLint](https://eslint.org) をリントとフォーマットの両方に使用しています。

##### IDE 設定

[ESLint 拡張機能](https://marketplace.visualstudio.com/items?itemName=dbaeumer.vscode-eslint)と一緒に [VS Code](https://code.visualstudio.com) を使用することをお勧めします。必要に応じて、編集中のコードを保存する際に自動修正とフォーマットを有効にできます：

```json [settings.json]
{
  "editor.codeActionsOnSave": {
    "source.fixAll": "never",
    "source.fixAll.eslint": "explicit"
  }
}
```

#### Prettier は使用しない

ESLint がすでにコードをフォーマットするように設定されているため、Prettier で機能を重複させる必要はありません。コードをフォーマットするには、`yarn lint --fix`、`pnpm lint --fix`、または `bun run lint --fix` を実行するか、IDE 設定については [ESLint セクション](#use-eslint)を参照してください。

エディターに Prettier がインストールされている場合は、競合を避けるためにプロジェクトで作業する際には無効にすることをお勧めします。

#### パッケージマネージャー

モジュール、ライブラリ、アプリのパッケージマネージャーとして `pnpm` をお勧めします。

プロジェクトと同じバージョンのパッケージマネージャーを使用していることを確認するために、Corepack を有効にすることが重要です。Corepack は新しい Node バージョンに組み込まれており、シームレスなパッケージマネージャーの統合を提供します。

有効にするには、以下を実行してください：

```bash [Terminal]
corepack enable
```

これは、コンピューターに Node.js がインストールされた後に一度だけ行えばよいです。

## ドキュメントスタイルガイド

ドキュメントは Nuxt の重要な部分です。私たちは直感的なフレームワークであることを目指しており、その大きな部分はエコシステム全体で開発者エクスペリエンスとドキュメントの両方が完璧であることを確実にすることです。👌

ドキュメントの改善に役立ついくつかのヒント：

* 可能な限り、_単純に_、_だけ_、_明らかに..._などの主観的な言葉を避ける。

  読者は異なる背景や経験を持つ可能性があることを念頭に置いてください。そのため、これらの言葉は意味を伝えず、有害になる可能性があります。

  ::caution{ icon="i-lucide-circle-x"}
  単純に関数がプロミスを返すことを確認してください。
  ::

  ::tip{icon="i-lucide-circle-check"}
  関数が [プロミス](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise)を返すことを確認してください。
  ::

* [能動態](https://developers.google.com/tech-writing/one/active-voice)を優先する。

  ::caution{icon="i-lucide-circle-x"}
  エラーが Nuxt によってスローされます。
