## Nuxt のアップグレード

### 最新リリース

Nuxt を [最新リリース](https://github.com/nuxt/nuxt/releases) にアップグレードするには、`nuxt upgrade` コマンドを使用します。

::code-group{sync="pm"}

```bash [npm]
npx nuxt upgrade
```

```bash [yarn]
yarn nuxt upgrade
```

```bash [pnpm]
pnpm nuxt upgrade
```

```bash [bun]
bun x nuxt upgrade
```

::

### Nightly Release Channel

リリース前に最新の Nuxt ビルドとテスト機能を使用するには、[nightly release channel](/docs/guide/going-further/nightly-release-channel) ガイドをお読みください。

::warning
nightly release channel の `latest` タグは現在 Nuxt v4 ブランチを追跡しており、現在破壊的変更が含まれる可能性が特に高いことを意味します &mdash; 注意してください！`"nuxt": "npm:nuxt-nightly@3x"` で 3.x ブランチの nightly リリースをオプトインできます。
::

## Nuxt 4 のテスト

Nuxt 4 は **2025年第2四半期にリリース予定** です。`compatibilityVersion: 4` で現在利用可能なすべての機能が含まれます。

リリースまでの間、Nuxt バージョン 3.12+ から Nuxt 4 の多くの破壊的変更をテストすることが可能です。

:video-accordion{title="Watch a video from Alexander Lichter showing how to opt in to Nuxt 4's breaking changes already" videoId="r4wFKlcJK6c"}

### Nuxt 4 へのオプトイン

まず、Nuxt を [最新リリース](https://github.com/nuxt/nuxt/releases) にアップグレードします。

その後、Nuxt 4 の動作に合わせるために `compatibilityVersion` を設定できます：

::code-collapse
```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  future: {
    compatibilityVersion: 4,
  },
  // すべての Nuxt v3 の動作を再有効化するために、以下のオプションを設定します：
  // srcDir: '.',
  // dir: {
  //   app: 'app'
  // },
  // experimental: {
  //   scanPageMeta: 'after-resolve',
  //   sharedPrerenderData: false,
  //   compileTemplate: true,
  //   resetAsyncDataToUndefined: true,
  //   templateUtils: true,
  //   relativeWatchPaths: true,
  //   normalizeComponentNames: false,
  //   spaLoadingTemplateLocation: 'within',
  //   parseErrorData: false,
  //   pendingWhenIdle: true,
  //   alwaysRunFetchOnKeyChange: true,
  //   defaults: {
  //     useAsyncData: {
  //       deep: true
  //     }
  //   }
  // },
  // features: {
  //   inlineStyles: true
  // },
  // unhead: {
  //   renderSSRHeadOptions: {
  //     omitLineBreaks: false
  //   }
  // }
})
```
::

::note
現在のところ、Nuxt 4 の動作をオプトインする各レイヤーで互換性バージョンを定義する必要があります。これは Nuxt 4 がリリースされた後は必要ありません。
::

`compatibilityVersion` を `4` に設定すると、Nuxt 設定全体のデフォルトが Nuxt v4 の動作をオプトインするように変更されますが、テスト時には上記のコメントアウトされた行に従って Nuxt v3 の動作を粒度で再有効化できます。その場合は、Nuxt やエコシステムで対応できるように問題を報告してください。

破壊的または重要な変更は、後方/前方互換性のための移行手順とともにここに記載されます。

::note
このセクションは最終リリースまで変更される可能性がありますので、`compatibilityVersion: 4` を使用して Nuxt 4 をテストしている場合は定期的にここをチェックしてください。
::

### Codemod を使用した移行

アップグレードプロセスを容易にするために、[Codemod](https://github.com/codemod-com/codemod) チームと協力して、いくつかのオープンソース codemod で多くの移行ステップを自動化しました。

::note
問題が発生した場合は、`npx codemod feedback` で Codemod チームに報告してください 🙏
::

Nuxt 4 codemod の完全なリスト、各々の詳細情報、そのソース、およびさまざまな実行方法については、[Codemod Registry](https://go.codemod.com/codemod-registry) をご覧ください。

このガイドで言及されているすべての codemod を、次の `codemod` レシピを使用して実行できます：

::code-group

```bash [npm]
npx codemod@latest nuxt/4/migration-recipe
```

```bash [yarn]
yarn dlx codemod@latest nuxt/4/migration-recipe
```

```bash [pnpm]
pnpm dlx codemod@latest nuxt/4/migration-recipe
```

```bash [bun]
bun x codemod@latest nuxt/4/migration-recipe
```

::

このコマンドは、すべての codemod を順次実行し、実行したくないものを選択解除するオプションがあります。各 codemod は、それぞれの変更とともに以下にリストされ、独立して実行できます。

### 新しいディレクトリ構造

🚦 **影響レベル**: 大

Nuxt は現在、新しいディレクトリ構造をデフォルトとしており、後方互換性があります（したがって、Nuxt がトップレベルの `pages/` ディレクトリなどの古い構造を使用していることを検出した場合、この新しい構造は適用されません）。

👉 [完全な RFC を見る](https://github.com/nuxt/nuxt/issues/26444)

#### 変更内容

* 新しい Nuxt のデフォルト `srcDir` はデフォルトで `app/` であり、ほとんどのものはそこから解決されます。
* `serverDir` は現在、`<srcDir>/server` ではなく `<rootDir>/server` をデフォルトとします
* `layers/`、`modules/`、`public/` はデフォルトで `<rootDir>` に対して相対的に解決されます
* [Nuxt Content v2.13+](https://github.com/nuxt/content/pull/2649) を使用している場合、`content/` は `<rootDir>` に対して相対的に解決されます
* 新しい `dir.app` が追加され、これは `router.options.ts` と `spa-loading-template.html` を探すディレクトリです - これはデフォルトで `<srcDir>/` です

<details>

<summary>v4 フォルダー構造の例。</summary>

```sh
.output/
.nuxt/
app/
  assets/
  components/
  composables/
  layouts/
  middleware/
  pages/
  plugins/
  utils/
  app.config.ts
  app.vue
  router.options.ts
content/
layers/
modules/
node_modules/
public/
server/
  api/
  middleware/
  plugins/
  routes/
  utils/
nuxt.config.ts
```

::note
この新しい構造では、`~` エイリアスは現在デフォルトで `app/` ディレクトリ（あなたの `srcDir`）を指します。つまり、`~/components` は `app/components/` に解決され、`~/pages` は `app/pages/` に解決されます。
::

</details>

👉 詳細については、[この変更を実装した PR](https://github.com/nuxt/nuxt/pull/27029) をご覧ください。

#### 変更理由

1. **パフォーマンス** - リポジトリのルートにすべてのコードを配置すると、FS ウォッチャーによって `.git/` と `node_modules/` フォルダーがスキャン/含まれるため、Mac 以外の OS で起動が大幅に遅れる問題が発生します。
1. **IDE の型安全性** - `server/` とアプリの残りの部分は、利用可能な異なるグローバルインポートを持つ 2つの完全に異なるコンテキストで実行されており、`server/` がアプリの残りの部分と同じフォルダーの _内部_ にないことを確認することは、IDE で良好な自動補完を確実に得るための重要な第一歩です。

:video-accordion{title="新しいディレクトリ構造に関する Vue School の動画を見る" videoId="1031028378" platform="vimeo"}

#### 移行手順

1. `app/` という新しいディレクトリを作成します。
1. `assets/`、`components/`、`composables/`、`layouts/`、`middleware/`、`pages/`、`plugins/`、`utils/` フォルダーと、`app.vue`、`error.vue`、`app.config.ts` をその下に移動します。`app/router-options.ts` または `app/spa-loading-template.html` がある場合、これらのパスは同じままです。
1. `nuxt.config.ts`、`content/`、`layers/`、`modules/`、`public/`、`server/` フォルダーが `app/` フォルダーの外側、プロジェクトのルートに残ることを確認してください。
1. 新しいディレクトリ構造で動作するように、`tailwindcss` や `eslint` の設定など、サードパーティの設定ファイルを更新することを忘れないでください（必要な場合 - `@nuxtjs/tailwindcss` は自動的に `tailwindcss` を正しく設定するはずです）。

::tip
`npx codemod@latest nuxt/4/file-structure` を実行して、この移行を自動化できます
::

ただし、移行は _必須ではありません_。現在のフォルダー構造を維持したい場合、Nuxt は自動検出するはずです。（検出しない場合は、問題を報告してください。）唯一の例外は、_すでに_ カスタム `srcDir` がある場合です。この場合、`modules/`、`public/`、`server/` フォルダーは、カスタム `srcDir` からではなく `rootDir` から解決されることに注意してください。必要に応じて、`dir.modules`、`dir.public`、`serverDir` を設定することでこれを上書きできます。

次の設定で v3 フォルダー構造を強制することもできます：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  // これは新しい srcDir のデフォルトを `app` からルートディレクトリに戻します
  srcDir: '.',
  // これは `router.options.ts` と `spa-loading-template.html` のディレクトリプレフィックスを指定します
  dir: {
    app: 'app'
  }
})
```

### シングルトンデータ取得レイヤー

🚦 **影響レベル**: 中

#### 変更内容

Nuxt のデータ取得システム（`useAsyncData` と `useFetch`）は、より良いパフォーマンスと一貫性のために大幅に再編成されました：

1. **同じキーの共有 ref**: 同じキーを持つ `useAsyncData` または `useFetch` のすべての呼び出しは、現在同じ `data`、`error`、`status` ref を共有します。これは、明示的なキーを持つすべての呼び出しが、競合する `deep`、`transform`、`pick`、`getCachedData`、`default` オプションを持ってはいけないことを意味します。

2. **`getCachedData` のより細かい制御**: `getCachedData` 関数は現在、ウォッチャーや `refreshNuxtData` の呼び出しによる場合でも、データが取得されるたびに呼び出されます。（以前は、新しいデータが常に取得され、これらの場合にこの関数は呼び出されませんでした。）キャッシュされたデータを使用するタイミングと再取得するタイミングをより細かく制御できるように、関数は現在リクエストの原因を含むコンテキストオブジェクトを受け取ります。

3. **リアクティブキーサポート**: キーとして computed ref、通常の ref、または getter 関数を使用できるようになり、自動データ再取得（およびデータの別途保存）が可能になります。

4. **データクリーンアップ**: `useAsyncData` で取得したデータを使用する最後のコンポーネントがアンマウントされると、Nuxt はメモリ使用量の継続的な増加を防ぐためにそのデータを削除します。

#### 変更理由

これらの変更は、メモリ使用量を改善し、`useAsyncData` の呼び出し間でのローディング状態の一貫性を高めるために行われました。

#### 移行手順

1. **一貫性のないオプションのチェック**: 同じキーで異なるオプションや取得関数を使用しているコンポーネントを確認してください。

   ```ts
   // This will now trigger a warning
   const { data: users1 } = useAsyncData('users', () => $fetch('/api/users'), { deep: false })
   const { data: users2 } = useAsyncData('users', () => $fetch('/api/users'), { deep: true })
   ```

   明示的なキー（およびカスタムオプション）を共有する `useAsyncData` の呼び出しを、独自のコンポーザブルに抽出することが有益な場合があります：

   ```ts [composables/useUserData.ts]
   export function useUserData(userId: string) {
     return useAsyncData(
       `user-${userId}`,
       () => fetchUser(userId),
       { 
         deep: true,
         transform: (user) => ({ ...user, lastAccessed: new Date() })
       }
     )
   }
   ```

2. **`getCachedData` の実装をアップデートする**：

   ```diff
   useAsyncData('key', fetchFunction, {
   -  getCachedData: (key, nuxtApp) => {
   -    return cachedData[key]
   -  }
   +  getCachedData: (key, nuxtApp, ctx) => {
   +    // ctx.cause - 'initial' | 'refresh:hook' | 'refresh:manual' | 'watch' のいずれか
   +    
   +    // 例: 手動リフレッシュではキャッシュを使用しない
   +    if (ctx.cause === 'refresh:manual') return undefined
   +    
   +    return cachedData[key]
   +  }
   })
   ```

または、当面はこの動作を無効にできます：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    granularCachedData: false,
    purgeCachedData: false
  }
})
```

### ルート メタデータの重複除去

🚦 **影響レベル**: 最小

#### 変更内容

`definePageMeta` を使用して、`name`、`path` などのいくつかのルート メタデータを設定できます。以前、これらはルート オブジェクトとルート メタデータの両方で利用可能でした（例：`route.name` と `route.meta.name`）。

現在、これらはルート オブジェクトでのみアクセスできます。

#### 変更理由

これは `experimental.scanPageMeta` をデフォルトで有効にした結果であり、パフォーマンスの最適化です。

#### 移行手順

移行は簡単なはずです：

```diff
  const route = useRoute()
  
- console.log(route.meta.name)
+ console.log(route.name)
```

### 正規化されたコンポーネント名

🚦 **影響レベル**: 中

Vue は、コンポーネント命名の Nuxt パターンと一致するコンポーネント名を生成するようになります。

#### 変更内容

デフォルトでは、手動で設定していない場合、Vue はコンポーネントのファイル名と一致するコンポーネント名を割り当てます。

```bash [ディレクトリ構造]
├─ components/
├─── SomeFolder/
├───── MyComponent.vue
```

この場合、Vue に関する限り、コンポーネント名は `MyComponent` になります。`<KeepAlive>` で使用したり、Vue DevTools で識別したりする場合は、この名前を使用する必要があります。

しかし、自動インポートするためには、`SomeFolderMyComponent` を使用する必要があります。

この変更により、これら 2つの値が一致し、Vue はコンポーネント命名の Nuxt パターンと一致するコンポーネント名を生成します。

#### 移行手順

`@vue/test-utils` の `findComponent` を使用するテストや、コンポーネント名に依存する `<KeepAlive>` で、更新された名前を使用していることを確認してください。

または、当面はこの動作を無効にできます：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizeComponentNames: false
  }
})
```

### Unhead v2

🚦 **影響レベル**: 最小

#### 変更内容

`<head>` タグを生成するために使用される [Unhead](https://unhead.unjs.io/) がバージョン 2 にアップデートされました。ほとんど互換性がありますが、低レベル API に対していくつかの破壊的変更が含まれます。

* 削除されたプロパティ：`vmid`、`hid`、`children`、`body`。
* Promise の入力はサポートされなくなりました。
* タグはデフォルトで Capo.js を使用してソートされるようになりました。

#### 移行手順

上記の変更は、アプリへの影響を最小限に抑える必要があります。

問題がある場合は、以下を確認してください：

* 削除されたプロパティを使用していないこと。

```diff
useHead({
  meta: [{ 
    name: 'description', 
    // meta タグには vmid や key は必要ありません    
-   vmid: 'description' 
-   hid: 'description'
  }]
})
```

* [Template Params](https://unhead.unjs.io/docs/head/guides/plugins/template-params) または [Alias Tag Sorting](https://unhead.unjs.io/docs/head/guides/plugins/alias-sorting) を使用している場合は、これらの機能に明示的にオプトインする必要があります。

```ts
import { TemplateParamsPlugin, AliasSortingPlugin } from '@unhead/vue/plugins'

export default defineNuxtPlugin({
  setup() {
    const unhead = injectHead()
    unhead.use(TemplateParamsPlugin)
    unhead.use(AliasSortingPlugin)
  }
})
```

必須ではありませんが、`@unhead/vue` からのインポートを `#imports` または `nuxt/app` にアップデートすることをお勧めします。

```diff
-import { useHead } from '@unhead/vue'
+import { useHead } from '#imports'
```

まだ問題がある場合は、`head.legacy` 設定を有効にして v1 の動作に戻すことができます。

```ts
export default defineNuxtConfig({
  unhead: {
    legacy: true,
  }
})
```

### SPA ローディング スクリーンの新しい DOM の場所

🚦 **影響レベル**: 最小

#### 変更内容

クライアントのみのページ（`ssr: false`）をレンダリングする場合、Nuxt アプリルート内でローディング スクリーン（`~/app/spa-loading-template.html` から - Nuxt 4 では `~/spa-loading-template.html` に変更されたことに注意）をオプションでレンダリングします：

```html
<div id="__nuxt">
  <!-- spa loading template -->
</div>
```

現在、Nuxt アプリルートと並んでテンプレートをレンダリングすることがデフォルトになりました：

```html
<div id="__nuxt"></div>
<!-- spa loading template -->
```

#### 変更理由

これにより、Vue アプリの suspense が解決されるまで SPA ローディング テンプレートが DOM に残り、白いフラッシュを防ぐことができます。

#### 移行手順

CSS や `document.queryElement` で SPA ローディング テンプレートをターゲットにしていた場合は、セレクターを更新する必要があります。この目的のために、新しい `app.spaLoaderTag` と `app.spaLoaderAttrs` 設定オプションを使用できます。

または、以前の動作に戻すこともできます：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    spaLoadingTemplateLocation: 'within',
  }
})
```

### パースされた `error.data`

🚦 **影響レベル**: 最小

`data` プロパティでエラーをスローすることは可能でしたが、これはパースされていませんでした。現在、これはパースされ、`error` オブジェクトで利用可能になりました。修正であるとはいえ、以前の動作に依存して手動でパースしていた場合は、技術的には破壊的変更です。

#### 移行手順

カスタム `error.vue` で `error.data` の追加のパーシングを削除してください：

```diff
  <script setup lang="ts">
  import type { NuxtError } from '#app'

  const props = defineProps({
    error: Object as () => NuxtError
  })

- const data = JSON.parse(error.data)
+ const data = error.data
  </script>
```

または、この変更を無効にできます：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    parseErrorData: false
  },
})
```

### より細かいインライン スタイル

🚦 **影響レベル**: 中

Nuxt は現在、グローバル CSS ではなく Vue コンポーネントのスタイルのみをインライン化します。

#### 変更内容

以前、Nuxt はグローバル スタイルを含むすべての CSS をインライン化し、別々の CSS ファイルへの `<link>` 要素を削除していました。現在、Nuxt は Vue コンポーネント（以前は別々の CSS チャンクを生成していた）に対してのみこれを行います。これは、別々のネットワーク リクエストを減らす（以前と同じように、初期ロードでページ別またはコンポーネント別の個別の `.css` ファイルへの別々のリクエストはありません）と同時に、単一のグローバル CSS ファイルのキャッシュを可能にし、初期リクエストのドキュメント ダウンロード サイズを減らすより良いバランスだと考えています。

#### 移行手順

この機能は完全に設定可能であり、`inlineStyles: true` を設定してコンポーネント別の CSS と同様にグローバル CSS もインライン化することで、以前の動作に戻すことができます。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  features: {
    inlineStyles: true
  }
})
```

### 解決後のページ メタのスキャン

🚦 **影響レベル**: 最小

#### 変更内容

現在、ページ メタデータ（`definePageMeta` で定義）を `pages:extend` フックを呼び出す前ではなく _後に_ スキャンします。

#### 変更理由

これは、ユーザーが `pages:extend` で追加したいページのメタデータをスキャンできるようにするためでした。新しい `pages:resolved` フックでページ メタデータを変更または上書きする機会を引き続き提供しています。

#### 移行手順

ページ メタデータを上書きしたい場合は、`pages:extend` ではなく `pages:resolved` で行ってください。

```diff
  export default defineNuxtConfig({
    hooks: {
-     'pages:extend'(pages) {
+     'pages:resolved'(pages) {
        const myPage = pages.find(page => page.path === '/')
        myPage.meta ||= {}
        myPage.meta.layout = 'overridden-layout'
      }
    }
  })
```

または、以前の動作に戻すこともできます：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    scanPageMeta: true
  }
})
```

### 共有プリレンダー データ

🚦 **影響レベル**: 中

#### 変更内容

以前の実験機能であった、異なるページ間で `useAsyncData` と `useFetch` 呼び出しからのデータを共有する機能を有効にしました。[元の PR](https://github.com/nuxt/nuxt/pull/24894) を参照してください。

#### 変更理由

この機能は、プリレンダーされたページ間でペイロード _データ_ を自動的に共有します。これにより、`useAsyncData` または `useFetch` を使用し、異なるページで同じデータをフェッチするサイトをプリレンダーする場合、大幅なパフォーマンス向上が得られます。

たとえば、サイトのすべてのページで `useFetch` 呼び出しが必要な場合（たとえば、メニューのナビゲーション データや CMS からのサイト設定を取得するため）、このデータは、それを使用する最初のページをプリレンダーするときに一度だけフェッチされ、その後他のページをプリレンダーするときに使用するためにキャッシュされます。

#### 移行手順

データの一意なキーが常に同じデータに解決されることを確認してください。たとえば、特定のページに関連するデータをフェッチするために `useAsyncData` を使用している場合は、そのデータを一意に識別するキーを提供する必要があります。（`useFetch` はこれを自動的に行うはずです。）

```ts [app/pages/test/[slug\\].vue]
// これは動的ページ（例：`[slug].vue`）では安全ではありません。
// ルート slug がフェッチされるデータに影響を与えるが、キーに反映されていないため Nuxt はそれを知ることができません。
const route = useRoute()
const { data } = await useAsyncData(async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
// 代わりに、フェッチされたデータを一意に識別するキーを使用する必要があります。
const { data } = await useAsyncData(route.params.slug, async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
```

または、この機能を無効にできます：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    sharedPrerenderData: false
  }
})
```

### `useAsyncData` と `useFetch` でのデフォルト `data` と `error` の値

🚦 **影響レベル**: 最小

#### 変更内容

`useAsyncData` から返される `data` と `error` オブジェクトは、デフォルトで `undefined` になります。

#### 変更理由

以前、`data` は `null` に初期化されていましたが、`clearNuxtData` で `undefined` にリセットされていました。`error` は `null` に初期化されていました。この変更は、より一貫性をもたらすためです。

#### 移行手順

`data.value` または `error.value` が `null` かどうかをチェックしていた場合は、代わりに `undefined` をチェックするようにこれらのチェックを更新できます。

::tip
`npx codemod@latest nuxt/4/default-data-error-value` を実行して、このステップを自動化できます
::

問題が発生した場合は、以前の動作に戻すことができます：

```ts twoslash [nuxt.config.ts]
// @errors: 2353
export default defineNuxtConfig({
  experimental: {
    defaults: {
      useAsyncData: {
        value: 'null',
        errorValue: 'null'
      }
    }
  }
})
```

これを行っている場合は問題を報告してください。私たちはこれを設定可能なまま保持する予定はありません。

### `useAsyncData` と `useFetch` で `refresh` を呼び出すときの `dedupe` オプションの非推奨 `boolean` 値の削除

🚦 **影響レベル**: 最小

#### 変更内容

以前は `refresh` に `dedupe: boolean` を渡すことが可能でした。これらは `cancel`（`true`）と `defer`（`false`）のエイリアスでした。

```ts twoslash [app.vue]
// @errors: 2322
const { refresh } = await useAsyncData(async () => ({ message: 'Hello, Nuxt!' }))

async function refreshData () {
  await refresh({ dedupe: true })
}
```

#### 変更理由

これらのエイリアスは、より明確にするために削除されました。

この問題は、`useAsyncData` のオプションとして `dedupe` を追加するときに発生し、boolean 値が結果的に _逆_ になってしまうため、私たちは boolean 値を削除しました。

`refresh({ dedupe: false })` は **この新しいリクエストのために既存のリクエストを _キャンセルしない_** ことを意味しました。しかし、`useAsyncData` のオプション内で `dedupe: true` を渡すことは **既存の保留中リクエストがある場合は新しいリクエストを行わない** ことを意味します。（[PR](https://github.com/nuxt/nuxt/pull/24564#pullrequestreview-1764584361) を参照してください。）

#### 移行手順

移行は簡単なはずです：

```diff
  const { refresh } = await useAsyncData(async () => ({ message: 'Hello, Nuxt 3!' }))
  
  async function refreshData () {
-   await refresh({ dedupe: true })
+   await refresh({ dedupe: 'cancel' })

-   await refresh({ dedupe: false })
+   await refresh({ dedupe: 'defer' })
  }
```

::tip
`npx codemod@latest nuxt/4/deprecated-dedupe-value` を実行して、このステップを自動化できます
::

### `useAsyncData` と `useFetch` で `data` をクリアするときのデフォルトの尊重

🚦 **影響レベル**: 最小

#### 変更内容

`useAsyncData` にカスタム `default` 値を提供した場合、`clear` または `clearNuxtData` を呼び出すときにこれが使用され、単に未設定にするのではなくデフォルト値にリセットされるようになりました。

#### 変更理由

多くの場合、ユーザーは、空の配列などの適切な空の値を設定して、反復処理するときに `null`/`undefined` をチェックする必要を回避します。これは、データをリセット/クリアするときに尊重されるべきです。

#### 移行手順

問題が発生した場合は、当面は以前の動作に戻すことができます：

```ts twoslash [nuxt.config.ts]
// @errors: 2353
export default defineNuxtConfig({
  experimental: {
    resetAsyncDataToUndefined: true,
  }
})
```

これを行っている場合は問題を報告してください。私たちはこれを設定可能なまま保持する予定はありません。

### `useAsyncData` と `useFetch` の `pending` 値の整合

🚦 **影響レベル**: 中

`useAsyncData`、`useFetch`、`useLazyAsyncData`、`useLazyFetch` から返される `pending` オブジェクトは、`status` も保留中のときのみ `true` になる算出プロパティになりました。

#### 変更内容

現在、`immediate: false` が渡された場合、最初のリクエストが行われるまで `pending` は `false` になります。これは、最初のリクエストが行われるまで `pending` が常に `true` だった以前の動作からの変更です。

#### 変更理由

これにより、`pending` の意味が、リクエストが進行中のときに同じく `pending` である `status` プロパティと整合されます。

#### 移行手順

`pending` プロパティに依存している場合は、ステータスも保留中のときのみ `pending` が `true` になる新しい動作をロジックが考慮していることを確認してください。

```diff
  <template>
-   <div v-if="!pending">
+   <div v-if="status === 'success'">
      <p>Data: {{ data }}</p>
    </div>
    <div v-else>
      <p>Loading...</p>
    </div>
  </template>
  <script setup lang="ts">
  const { data, pending, execute, status } = await useAsyncData(() => fetch('/api/data'), {
    immediate: false
  })
  onMounted(() => execute())
  </script>
```

または、一時的に以前の動作に戻すこともできます：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    pendingWhenIdle: true
  }
})
```

### `useAsyncData` と `useFetch` のキー変更動作

🚦 **影響レベル**: 中

#### 変更内容

`useAsyncData` または `useFetch` でリアクティブなキーを使用するとき、Nuxt はキーが変更されたときに自動的にデータを再フェッチします。`immediate: false` が設定されている場合、`useAsyncData` はデータがすでに一度フェッチされている場合のみ、キーが変更されたときにデータをフェッチします。

以前、`useFetch` はわずかに異なる動作をしていました。キーが変更されたときに常にデータをフェッチしていました。

現在、`useFetch` と `useAsyncData` は一貫して動作します - データがすでに一度フェッチされている場合のみ、キーが変更されたときにデータをフェッチします。

#### 変更理由

これにより、`useAsyncData` と `useFetch` 間の一貫した動作が確保され、予期しないフェッチが防げるようになります。`immediate: false` を設定している場合は、`refresh` または `execute` を呼び出す必要があります。そうしないと、`useFetch` または `useAsyncData` でデータがフェッチされることはありません。

#### 移行手順

この変更は一般的に期待される動作を改善するはずですが、即座実行されない `useFetch` のキーやオプションの変更を期待していた場合は、最初の時に手動でトリガーする必要があります。

```diff
  const id = ref('123')
  const { data, execute } = await useFetch('/api/test', {
    query: { id },
    immediate: false
  )
+ watch(id, execute, { once: true })
```

この動作をオプトアウトするには：

```ts
// または Nuxt 設定でグローバルに
export default defineNuxtConfig({
  experimental: {
    alwaysRunFetchOnKeyChange: true
  }
})
```

### `useAsyncData` と `useFetch` のシャロー データ リアクティビティ

🚦 **影響レベル**: 最小

`useAsyncData`、`useFetch`、`useLazyAsyncData`、`useLazyFetch` から返される `data` オブジェクトは、`ref` ではなく `shallowRef` になりました。

#### 変更内容

新しいデータがフェッチされたとき、オブジェクト全体が置き換えられるため、`data` に依存するものは引き続きリアクティブになります。しかし、コードがそのデータ構造の _内部_ のプロパティを変更しても、これはアプリのリアクティビティをトリガーしません。

#### 変更理由

これにより、Vue がすべてのプロパティ/配列の変更を監視する必要がなくなるため、深くネストされたオブジェクトや配列に対して **大幅な** パフォーマンス向上が得られます。ほとんどの場合、`data` は不変であるべきです。

#### 移行手順

ほとんどの場合、移行手順は必要ありませんが、データ オブジェクトのリアクティビティに依存している場合は、2つのオプションがあります：

1. コンポーザブル単位で深いリアクティビティに粒度を細かくオプトインできます：
   ```diff
   - const { data } = useFetch('/api/test')
   + const { data } = useFetch('/api/test', { deep: true })
   ```
1. プロジェクト全体でデフォルト動作を変更できます（非推奨）：
   ```ts twoslash [nuxt.config.ts]
   export default defineNuxtConfig({
     experimental: {
       defaults: {
         useAsyncData: {
           deep: true
         }
       }
     }
   })
   ```

::tip
必要に応じて、`npx codemod@latest nuxt/4/shallow-function-reactivity` を実行して、このステップを自動化できます
::

### `builder:watch` の絶対ウォッチ パス

🚦 **影響レベル**: 最小

#### 変更内容

Nuxt の `builder:watch` フックは、プロジェクトの `srcDir` に相対ではなく、絶対パスを発行するようになりました。

#### 変更理由

これにより、`srcDir` の外部にあるパスの監視をサポートでき、レイヤーやその他のより複雑なパターンのサポートが向上します。

#### 移行手順

私たちは、このフックを使用していることを把握している公開 Nuxt モジュールをすでに積極的に移行しました。[イシュー #25339](https://github.com/nuxt/nuxt/issues/25339) を参照してください。

しかし、`builder:watch` フックを使用しているモジュール作成者で、後方/前方互換性を維持したい場合は、以下のコードを使用して、Nuxt v3 と Nuxt v4 の両方でコードが同じように動作することを確実にできます：

```diff
+ import { relative, resolve } from 'node:fs'
  // ...
  nuxt.hook('builder:watch', async (event, path) => {
+   path = relative(nuxt.options.srcDir, resolve(nuxt.options.srcDir, path))
    // ...
  })
```

::tip
`npx codemod@latest nuxt/4/absolute-watch-path` を実行して、このステップを自動化できます
::

### `window.__NUXT__` オブジェクトの削除

#### 変更内容

アプリのハイドレーションが完了した後に、グローバル `window.__NUXT__` オブジェクトを削除します。

#### 変更理由

これにより、マルチアプリ パターン ([#21635](https://github.com/nuxt/nuxt/issues/21635)) への道が開かれ、Nuxt アプリ データにアクセスする単一の方法 - `useNuxtApp()` に集中できるようになります。

#### 移行手順

データはまだ利用可能ですが、`useNuxtApp().payload` でアクセスできます：

```diff
- console.log(window.__NUXT__)
+ console.log(useNuxtApp().payload)
```

### ディレクトリ index スキャン

🚦 **影響レベル**: 中

#### 変更内容

`middleware/` フォルダー内の子フォルダーも `index` ファイルがスキャンされ、これらはプロジェクトのミドルウェアとして登録されるようになりました。

#### 変更理由

Nuxt は `middleware/` や `plugins/` を含むいくつかのフォルダーを自動的にスキャンします。

`plugins/` フォルダー内の子フォルダーは `index` ファイルがスキャンされ、スキャンされるディレクトリ間でこの動作を一貫させたいと考えました。

#### 移行手順

おそらく移行は必要ありませんが、以前の動作に戻したい場合は、これらのミドルウェアをフィルターするためのフックを追加できます：

```ts
export default defineNuxtConfig({
  hooks: {
    'app:resolve'(app) {
      app.middleware = app.middleware.filter(mw => !/\/index\.[^/]+$/.test(mw.path))
    }
  }
})
```

### テンプレートコンパイルの変更

🚦 **影響レベル**: 最小

#### 変更内容

以前、Nuxt は `.ejs` ファイル形式/構文を使用してファイルシステム上にあるテンプレートをコンパイルするために `lodash/template` を使用していました。

さらに、これらのテンプレート内でコード生成に使用できるいくつかのテンプレートユーティリティ（`serialize`、`importName`、`importSources`）を提供していましたが、これらは現在削除されています。

#### 変更理由

Nuxt v3 では、より柔軟性がありパフォーマンスの高い `getContents()` 関数を使用した「仮想」構文に移行しました。

さらに、`lodash/template` は続けてセキュリティの問題を抱えています。これらは、ランタイムではなくビルド時に信頼できるコードで使用されているため、Nuxt プロジェクトには実際には適用されません。しかし、セキュリティ監査には依然として表示されます。さらに、`lodash` は大きな依存関係であり、ほとんどのプロジェクトでは使用されていません。

最後に、Nuxt 内でコードシリアライゼーション関数を直接提供することは理想的ではありません。代わりに、[unjs/knitwork](http://github.com/unjs/knitwork) のようなプロジェクトを維持しており、これらはあなたのプロジェクトの依存関係にすることができ、Nuxt 自体のアップグレードを必要とせずにセキュリティの問題を直接報告/解決できます。

#### 移行手順

EJS 構文を使用するモジュールを更新するための PR を作成しましたが、自分で行う必要がある場合は、3つの後方/前方互換の代替手段があります：

* 文字列補間ロジックを `getContents()` に直接移動する。
* https://github.com/nuxt-modules/color-mode/pull/240 のように、置換を処理するカスタム関数を使用する。
* Nuxt ではなく _あなたの_ プロジェクトの依存関係として、`es-toolkit/compat`（lodash template のドロップイン置換）を使用する：

```diff
+ import { readFileSync } from 'node:fs'
+ import { template } from 'es-toolkit/compat'
  // ...
  addTemplate({
    fileName: 'appinsights-vue.js'
    options: { /* some options */ },
-   src: resolver.resolve('./runtime/plugin.ejs'),
+   getContents({ options }) {
+     const contents = readFileSync(resolver.resolve('./runtime/plugin.ejs'), 'utf-8')
+     return template(contents)({ options })
+   },
  })
```

最後に、テンプレートユーティリティ（`serialize`、`importName`、`importSources`）を使用している場合は、`knitwork` のユーティリティで次のように置き換えることができます：

```ts
import { genDynamicImport, genImport, genSafeVariableName } from 'knitwork'

const serialize = (data: any) => JSON.stringify(data, null, 2).replace(/"{(.+)}"(?=,?$)/gm, r => JSON.parse(r).replace(/^{(.*)}$/, '$1'))

const importSources = (sources: string | string[], { lazy = false } = {}) => {
  return toArray(sources).map((src) => {
    if (lazy) {
      return `const ${genSafeVariableName(src)} = ${genDynamicImport(src, { comment: `webpackChunkName: ${JSON.stringify(src)}` })}`
    }
    return genImport(src, genSafeVariableName(src))
  }).join('\n')
}

const importName = genSafeVariableName
```

::tip
`npx codemod@latest nuxt/4/template-compilation-changes` を実行してこの手順を自動化できます
::

### TypeScript 設定の変更

🚦 **影響レベル**: 最小

#### 変更内容

Nuxt は現在、より良い型チェック体験を提供するために、異なるコンテキスト用の別々の TypeScript 設定を生成します：

1. **新しい TypeScript 設定ファイル**: Nuxt は現在追加の TypeScript 設定を生成します：
   * `.nuxt/tsconfig.app.json` - アプリコード用（Vue コンポーネント、コンポーザブルなど）
   * `.nuxt/tsconfig.server.json` - サーバーサイドコード用（Nitro/server ディレクトリ）  
   * `.nuxt/tsconfig.node.json` - ビルド時コード用（モジュール、`nuxt.config.ts` など）
   * `.nuxt/tsconfig.json` - 後方互換性のためのレガシー設定

2. **後方互換性**: `.nuxt/tsconfig.json` を拡張する既存のプロジェクトは以前と同じように動作し続けます。

3. **オプトインプロジェクト参照**: 新しいプロジェクトやより良い型チェックを望むプロジェクトは、TypeScript のプロジェクト参照機能を採用できます。

4. **コンテキスト固有の型チェック**: 各コンテキストは現在、その固有の環境に適切なコンパイラオプションと includes/excludes を持っています。

5. **新しい `typescript.nodeTsConfig` オプション**: Node.js ビルド時コードの TypeScript 設定をカスタマイズできるようになりました。

#### 変更理由

この変更はいくつかのメリットを提供します：

1. **より良い型安全性**: 各コンテキスト（アプリ、サーバー、ビルド時）が、コンテキスト固有のグローバルと API で適切な型チェックを受けられます。
2. **改善された IDE 体験**: コードベースの異なる部分に対して、より良い IntelliSense とエラーレポートが提供されます。
3. **よりクリーンな分離**: サーバーコードがクライアントサイド API を誤って推奨したり、その逆が起こったりしなくなります。
4. **パフォーマンス**: TypeScript は適切にスコープされた設定でより効率的にコードをチェックできます。

例えば、自動インポートは `nuxt.config.ts` では利用できません（しかし以前は TypeScript でフラグが立てられませんでした）。そして IDE は `server/` ディレクトリの `tsconfig.json` によってヒントされた別のコンテキストを認識していましたが、これは型チェックに反映されていませんでした（別のステップが必要でした）。

#### 移行手順

**移行は必要ありません** - 既存のプロジェクトは以前と同じように動作し続けます。

ただし、改善された型チェックを活用するには、新しいプロジェクト参照アプローチにオプトインできます：

1. **ルートの `tsconfig.json` を更新**してプロジェクト参照を使用します：

   ```json
   {
     "files": [],
     "references": [
       { "path": "./.nuxt/tsconfig.app.json" },
       { "path": "./.nuxt/tsconfig.server.json" },
       { "path": "./.nuxt/tsconfig.node.json" }
     ]
   }
   ```

2. **手動で作成したサーバー `tsconfig.json` ファイルを削除**します（`.nuxt/tsconfig.server.json` を拡張していた `server/tsconfig.json` など）。

3. **型チェックスクリプトを更新**してプロジェクト参照用のビルドフラグを使用します：

   ```diff
   - "typecheck": "nuxt prepare && vue-tsc --noEmit"
   + "typecheck": "nuxt prepare && vue-tsc -b --noEmit"
   ```

4. **Node.js TypeScript オプションを設定**（必要な場合）：
   <!-- @case-police-ignore tsConfig -->

   ```ts
   export default defineNuxtConfig({
     typescript: {
       // アプリ/サーバー TypeScript 設定をカスタマイズ
       tsConfig: {
         compilerOptions: {
           strict: true
         }
       },
       // ビルド時 TypeScript 設定をカスタマイズ  
       nodeTsConfig: {
         compilerOptions: {
           strict: true
         }
       }
     }
   })
   ```

5. **CI/ビルドスクリプトを更新**して、TypeScript チェックを実行するものが新しいプロジェクト参照アプローチを使用するようにします。

新しい設定は、オプトインするプロジェクトにとってより良い型安全性と IntelliSense を提供し、既存のセットアップとの完全な後方互換性を維持します。

### 実験機能の削除

🚦 **影響レベル**: 最小

#### 変更内容

4つの実験機能が Nuxt 4 ではもはや設定できなくなりました：

* `experimental.treeshakeClientOnly` は `true` になります（v3.0 以降のデフォルト）
* `experimental.configSchema` は `true` になります（v3.3 以降のデフォルト）
* `experimental.polyfillVueUseHead` は `false` になります（v3.4 以降のデフォルト）
* `experimental.respectNoSSRHeader` は `false` になります（v3.4 以降のデフォルト）
* `vite.devBundler` はもはや設定できません - デフォルトで `vite-node` を使用します

#### 変更理由

これらのオプションはしばらくの間現在の値に設定されており、引き続き設定可能である必要があると信じる理由はありません。

#### 移行手順

* `polyfillVueUseHead` は[このプラグイン](https://github.com/nuxt/nuxt/blob/f209158352b09d1986aa320e29ff36353b91c358/packages/nuxt/src/head/runtime/plugins/vueuse-head-polyfill.ts#L10-L11)でユーザーランドで実装可能です

* `respectNoSSRHeader` は[サーバーミドルウェア](https://github.com/nuxt/nuxt/blob/c660b39447f0d5b8790c0826092638d321cd6821/packages/nuxt/src/core/runtime/nitro/no-ssr.ts#L8-L9)でユーザーランドで実装可能です

### トップレベル `generate` 設定の削除

🚦 **影響レベル**: 最小

#### 変更内容

トップレベルの `generate` 設定オプションは Nuxt 4 ではもはや利用できません。これには、すべてのプロパティが含まれます：

* `generate.exclude` - 事前レンダリングからルートを除外するため
* `generate.routes` - 事前レンダリングするルートを指定するため

#### 変更理由

トップレベルの `generate` 設定は Nuxt 2 からの遺物でした。私たちはしばらくの間 `nitro.prerender` をサポートしており、これが Nuxt 3+ で事前レンダリングを設定する好ましい方法です。

#### 移行手順

`generate` 設定を対応する `nitro.prerender` オプションに置き換えます：

```diff
export default defineNuxtConfig({
- generate: {
-   exclude: ['/admin', '/private'],
-   routes: ['/sitemap.xml', '/robots.txt']
- }
+ nitro: {
+   prerender: {
+     ignore: ['/admin', '/private'],
+     routes: ['/sitemap.xml', '/robots.txt']
+   }
+ }
})
```

::read-more{to="https://nitro.build/config/#prerender"}
Nitro の事前レンダリング設定オプションについて詳しく読む。
::
