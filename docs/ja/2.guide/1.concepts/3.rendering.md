Nuxt はさまざまなレンダリングモード、[ユニバーサルレンダリング](#universal-rendering)、[クライアントサイドレンダリング](#client-side-rendering) をサポートしていますが、[ハイブリッドレンダリング](#hybrid-rendering) や [CDN Edge サーバー](#edge-side-rendering) でアプリケーションをレンダリングする可能性も提供しています。

ブラウザーとサーバーの両方が JavaScript コードを解釈して Vue.js コンポーネントを HTML 要素に変換できます。このステップは **レンダリング** と呼ばれます。Nuxt は **ユニバーサル** と **クライアントサイド** の両方のレンダリングをサポートしています。この 2 つのアプローチにはメリットとデメリットがあり、それらを説明します。

デフォルトで、Nuxt はより優れたユーザーエクスペリエンス、パフォーマンス、検索エンジンインデックシングの最適化を提供するために **ユニバーサルレンダリング** を使用しますが、[一行の設定](/docs/api/nuxt-config#ssr)でレンダリングモードを切り替えることができます。

## ユニバーサルレンダリング

このステップは、PHP や Ruby アプリケーションで実行される伝統的な **サーバーサイドレンダリング** と似ています。ユニバーサルレンダリングが有効な状態でブラウザーが URL をリクエストすると、Nuxt はサーバー環境で JavaScript（Vue.js）コードを実行し、完全にレンダリングされた HTML ページをブラウザーに返します。ページが事前に生成されている場合、Nuxt はキャッシュから完全にレンダリングされた HTML ページを返すこともあります。ユーザーはクライアントサイドレンダリングとは対照的に、アプリケーションの初期コンテンツの全体を直ちに取得できます。

HTML ドキュメントがダウンロードされると、ブラウザーはこれを解釈し、Vue.js がドキュメントを制御します。かつてサーバーで実行されたのと同じ JavaScript コードが、クライアント（ブラウザー）でバックグラウンドで **再び** 実行され、HTML にリスナーをバインドすることでインタラクティビティを有効にします（したがって **ユニバーサルレンダリング**）。これは **ハイドレーション** と呼ばれます。ハイドレーションが完了すると、ページは動的インターフェースやページトランジションなどの恩恵を享受できます。

ユニバーサルレンダリングにより、Nuxt アプリケーションはクライアントサイドレンダリングのメリットを保ちながら、高速なページ読み込み時間を提供できます。さらに、コンテンツはすでに HTML ドキュメントに存在するため、クローラーはオーバーヘッドなしにインデックシングできます。

![Users can access the static content when the HTML document is loaded. Hydration then allows page's interactivity](/assets/docs/concepts/rendering/ssr.svg)

**サーバーレンダリングされるものとクライアントレンダリングされるものは何ですか？**

ユニバーサルレンダリングモードで Vue ファイルのどの部分がサーバーで、またはクライアントで実行されるかを尋ねるのは普通のことです。

```vue [app.vue]
<script setup lang="ts">
const counter = ref(0); // サーバーとクライアントの両方の環境で実行されます

const handleClick = () => {
  counter.value++; // クライアント環境でのみ実行されます
};
</script>

<template>
  <div>
    <p>Count: {{ counter }}</p>
    <button @click="handleClick">Increment</button>
  </div>
</template>
```

初回リクエストでは、`counter` ref は `<p>` タグの中でレンダリングされるため、サーバーで初期化されます。`handleClick` の内容はここでは実行されません。ブラウザーでのハイドレーション中に、`counter` ref は再初期化されます。`handleClick` は最終的にボタンにバインドされます。したがって、`handleClick` の本体は常にブラウザー環境で実行されると推論するのが理にかなっています。

[ミドルウェア](/docs/guide/directory-structure/middleware)と[ページ](/docs/guide/directory-structure/pages)はサーバーとハイドレーション中のクライアントで実行されます。[プラグイン](/docs/guide/directory-structure/plugins)はサーバー、クライアント、または両方でレンダリングされる可能性があります。[コンポーネント](/docs/guide/directory-structure/components)もクライアントでのみ実行されるように強制できます。[コンポーザブル](/docs/guide/directory-structure/composables)と[ユーティリティ](/docs/guide/directory-structure/utils)は、その使用コンテキストに基づいてレンダリングされます。

**サーバーサイドレンダリングのメリット：**
- **パフォーマンス**: ブラウザーは JavaScript で生成されたコンテンツよりも静的コンテンツをはるかに高速に表示できるため、ユーザーはページのコンテンツに即座にアクセスできます。同時に、Nuxt はハイドレーションプロセス中にウェブアプリケーションのインタラクティビティを保持します。
- **検索エンジン最適化**: ユニバーサルレンダリングは、古典的なサーバーアプリケーションと同様に、ページの完全な HTML コンテンツをブラウザーに配信します。ウェブクローラーはページのコンテンツを直接インデックシングできるため、ユニバーサルレンダリングは迅速にインデックシングしたいコンテンツにとって素晴らしい選択となります。

**サーバーサイドレンダリングのデメリット：**
- **開発制約**: サーバーとブラウザー環境は同じ API を提供せず、両方でシームレスに実行できるコードを書くのが難しい場合があります。幸いなことに、Nuxt はコードの一部がどこで実行されるかを判断するためのガイドラインと特定の変数を提供しています。
- **コスト**: ページをオンザフライでレンダリングするためにサーバーが実行中である必要があります。これは伝統的なサーバーと同様に月額コストが発生します。しかし、ブラウザーがクライアントサイドナビゲーションを引き継ぐユニバーサルレンダリングのおかげで、サーバー呼び出しは大幅に減少します。[エッジサイドレンダリング](#edge-side-rendering)を活用することでコスト削減が可能です。

ユニバーサルレンダリングは非常に汎用性が高く、ほぼあらゆるユースケースに対応でき、特にコンテンツ中心のウェブサイトに適しています：**ブログ、マーケティングウェブサイト、ポートフォリオ、e コマースサイト、マーケットプレイス**。

::tip
ハイドレーションミスマッチなしに Vue コードを書く方法のより多くの例については、[Vue ドキュメント](https://vuejs.org/guide/scaling-up/ssr.html#hydration-mismatch)をご覧ください。
::

::important
ブラウザー API に依存して副作用を持つライブラリをインポートする場合は、それをインポートするコンポーネントがクライアントサイドでのみ呼び出されるようにしてください。バンドラーは副作用を含むモジュールのインポートを tree-shake しません。
::

## クライアントサイドレンダリング

標準では、伝統的な Vue.js アプリケーションはブラウザー（または **クライアント**）でレンダリングされます。その後、ブラウザーが現在のインターフェースを作成するための命令を含むすべての JavaScript コードをダウンロードして解析した後、Vue.js が HTML 要素を生成します。

![Users have to wait for the browser to download, parse and execute the JavaScript before seeing the page's content](/assets/docs/concepts/rendering/csr.svg)

**クライアントサイドレンダリングのメリット：**
- **開発速度**: 完全にクライアントサイドで作業する際、`window` オブジェクトなどのブラウザー専用 API を使用することで、コードのサーバー互換性を心配する必要がありません。
- **より安価**: JavaScript をサポートするプラットフォームで実行する必要があるため、サーバーを実行することはインフラストラクチャコストを追加します。クライアント専用アプリケーションは、HTML、CSS、JavaScript ファイルを使用して任意の静的サーバーでホストできます。
- **オフライン**: コードが完全にブラウザーで実行されるため、インターネットが利用できない間も適切に動作し続けることができます。

**クライアントサイドレンダリングのデメリット：**
- **パフォーマンス**: ユーザーはブラウザーが JavaScript ファイルをダウンロード、解析、実行するのを待つ必要があります。ダウンロード部分についてはネットワークに、解析と実行についてはユーザーのデバイスに依存するため、これには時間がかかり、ユーザーエクスペリエンスに影響を与える可能性があります。
- **検索エンジン最適化**: クライアントサイドレンダリングで配信されるコンテンツのインデックシングと更新には、サーバーレンダリングされた HTML ドキュメントよりも時間がかかります。これは前述したパフォーマンスの欠点に関連しており、検索エンジンクローラーはページをインデックシングする最初の試行時にインターフェースが完全にレンダリングされるまで待機しません。純粋なクライアントサイドレンダリングでは、コンテンツが検索結果ページに表示され更新されるまでにより多くの時間がかかります。

クライアントサイドレンダリングは、インデックシングが不要で、ユーザーが頻繁に訪問するような高度にインタラクティブな **ウェブアプリケーション** に適した選択です。ブラウザーキャッシュを活用して後続の訪問でダウンロードフェーズをスキップできるため、**SaaS、バックオフィスアプリケーション、オンラインゲーム** などに向いています。

Nuxt でクライアントサイドのみのレンダリングを有効にするには、`nuxt.config.ts` で以下のように設定します：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  ssr: false
})
```

::note
`ssr: false` を使用する場合は、`~/spa-loading-template.html` に HTML ファイルを配置して、アプリがハイドレートされるまでレンダリングされるローディング画面に使用したい HTML を記述する必要があります。
:read-more{title="SPA Loading Template" to="/docs/api/configuration/nuxt-config#spaloadingtemplate"}
::

### 静的クライアントレンダリングアプリのデプロイ

`nuxt generate` または `nuxt build --prerender` コマンドを使用してアプリを [静的ホスティング](/docs/getting-started/deployment#static-hosting) にデプロイする場合、デフォルトで Nuxt は各ページを個別の静的 HTML ファイルとしてレンダリングします。

::warning
`nuxt generate` または `nuxt build --prerender` コマンドでアプリをプリレンダリングする場合、出力フォルダーにサーバーが含まれないため、サーバーエンドポイントを使用することはできません。サーバー機能が必要な場合は、代わりに `nuxt build` を使用してください。
::

純粋にクライアントサイドレンダリングを使用している場合、これは不要かもしれません。単一の `index.html` ファイルと、`200.html` および `404.html` のフォールバックのみが必要で、これらをすべてのリクエストに対して配信するよう静的ウェブホストに指示できます。

これを実現するために、ルートのプリレンダリング方法を変更できます。`nuxt.config.ts` の [フック](/docs/api/advanced/hooks#nuxt-hooks-build-time) に以下を追加してください：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  hooks: {
    'prerender:routes' ({ routes }) {
      routes.clear() // デフォルト以外のルートは生成しない
    }
  },
})
```

これにより 3 つのファイルが生成されます：

- `index.html`
- `200.html`
- `404.html`

`200.html` と `404.html` は、使用しているホスティングプロバイダーにとって有用かもしれません。

#### クライアントフォールバック生成のスキップ

クライアントレンダリングアプリをプリレンダリングする際、Nuxt はデフォルトで `index.html`、`200.html`、`404.html` ファイルを生成します。ただし、ビルド時にこれらのファイル（の一部またはすべて）の生成を防ぐ必要がある場合は、[Nitro](/docs/getting-started/prerendering#prerendergenerate-nitro-hook) の `'prerender:generate'` フックを使用できます。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  ssr: false,
  nitro: {
    hooks: {
      'prerender:generate'(route) {
        const routesToSkip = ['/index.html', '/200.html', '/404.html']
        if (routesToSkip.includes(route.route)) {
          route.skip = true
        }
      }
    }
  }
})
```

## ハイブリッドレンダリング

ハイブリッドレンダリングは **ルートルール** を使用してルートごとに異なるキャッシュルールを許可し、特定の URL への新しいリクエストに対してサーバーがどのように応答すべきかを決定します。

以前は Nuxt アプリケーションとサーバーのすべてのルート/ページが、ユニバーサルまたはクライアントサイドの同じレンダリングモードを使用する必要がありました。さまざまなケースで、一部のページはビルド時に生成され、他のページはクライアントサイドでレンダリングされるべき場合があります。たとえば、管理者セクションを持つコンテンツウェブサイトを考えてみてください。すべてのコンテンツページは主に静的で一度生成されるべきですが、管理者セクションはユーザー登録が必要で、よりダイナミックなアプリケーションのように振る舞います。

Nuxt にはルートルールとハイブリッドレンダリングサポートが含まれています。ルートルールを使用して、Nuxt ルートのグループに対してルールを定義し、レンダリングモードを変更したり、ルートに基づいてキャッシュ戦略を割り当てたりできます！

Nuxt サーバーは自動的に対応するミドルウェアを登録し、[Nitro キャッシュレイヤー](https://nitro.build/guide/cache) を使用してルートをキャッシュハンドラーでラップします。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    // ホームページはビルド時にプリレンダリング
    '/': { prerender: true },
    // 商品ページはオンデマンドで生成、バックグラウンドで再検証、API レスポンスが変更されるまでキャッシュ
    '/products': { swr: true },
    // 商品詳細ページはオンデマンドで生成、バックグラウンドで再検証、1 時間（ 3600 秒）キャッシュ
    '/products/**': { swr: 3600 },
    // ブログ投稿ページはオンデマンドで生成、バックグラウンドで再検証、CDN で1 時間（ 3600 秒）キャッシュ
    '/blog': { isr: 3600 },
    // ブログ個別投稿ページは次のデプロイまで一度だけオンデマンドで生成、CDN でキャッシュ
    '/blog/**': { isr: true },
    // 管理者ダッシュボードはクライアントサイドのみでレンダリング
    '/admin/**': { ssr: false },
    // API ルートに CORS ヘッダーを追加
    '/api/**': { cors: true },
    // 旧い URL をリダイレクト
    '/old-page': { redirect: '/new-page' }
  }
})
```

### ルートルール

使用できる異なるプロパティは以下の通りです：
- `redirect: string`{lang=ts} - サーバーサイドリダイレクトを定義します。
- `ssr: boolean`{lang=ts} - アプリのセクションの HTML のサーバーサイドレンダリングを無効にし、`ssr: false` でブラウザーでのみレンダリングさせます。
- `cors: boolean`{lang=ts} - `cors: true` で CORS ヘッダーを自動的に追加します - `headers` で上書きすることで出力をカスタマイズできます。
- `headers: object`{lang=ts} - サイトのセクションに特定のヘッダーを追加します - たとえば、アセットに。
- `swr: number | boolean`{lang=ts} - サーバーレスポンスにキャッシュヘッダーを追加し、設定可能な TTL（Time To Live）でサーバーまたはリバースプロキシにキャッシュします。Nitro の `node-server` プリセットは完全なレスポンスをキャッシュできます。TTL が期限切れすると、ページがバックグラウンドで再生成される間、キャッシュされたレスポンスが送信されます。`true` が使用される場合、MaxAge なしで `stale-while-revalidate` ヘッダーが追加されます。
- `isr: number | boolean`{lang=ts} - 動作は `swr` と同じですが、これをサポートするプラットフォーム（現在 Netlify または Vercel）で CDN キャッシュにレスポンスを追加できる点が異なります。`true` が使用される場合、コンテンツは CDN 内で次のデプロイまで永続します。
- `prerender: boolean`{lang=ts} - ビルド時にルートをプリレンダリングし、静的アセットとしてビルドに含めます。
- `noScripts: boolean`{lang=ts} - サイトのセクションの Nuxt スクリプトと JS リソースヒントのレンダリングを無効にします。
- `appMiddleware: string | string[] | Record<string, boolean>`{lang=ts} - アプリケーションの Vue アプリ部分（つまり Nitro ルートではない）内のページパスに対して実行するべきまたは実行すべきでないミドルウェアを定義できます。

可能な限り、ルートルールは最適なパフォーマンスのためにデプロイメントプラットフォームのネイティブルールに自動的に適用されます（現在 Netlify と Vercel がサポートされています）。

::important
[`nuxt generate`](/docs/api/commands/generate) を使用する場合はハイブリッドレンダリングが利用できないことに注意してください。
::

## エッジサイドレンダリング

エッジサイドレンダリング（ESR）は Nuxt に導入された強力な機能で、コンテンツ配信ネットワーク（CDN）のエッジサーバーを介して、ユーザーにより近い場所で Nuxt アプリケーションをレンダリングできます。ESR を活用することで、パフォーマンスの向上とレイテンシの減少を確実にし、これにより向上したユーザーエクスペリエンスを提供できます。

ESR では、レンダリングプロセスがネットワークの「エッジ」- CDN のエッジサーバーにプッシュされます。ESR は実際のレンダリングモードというよりもデプロイメントターゲットであることに注意してください。

ページのリクエストが行われると、元のサーバーまで行くのではなく、最も近いエッジサーバーがリクエストをインターセプトします。このサーバーがページの HTML を生成し、ユーザーに送り返します。このプロセスはデータが移動する物理的距離を最小化し、**レイテンシを減少させてページをより高速に読み込みます**。

エッジサイドレンダリングは、Nuxt を動かす [サーバーエンジン](/docs/guide/concepts/server-engine) である [Nitro](https://nitro.build/) のおかげで可能です。Node.js、Deno、Cloudflare Workers などのクロスプラットフォームサポートを提供します。

現在 ESR を活用できるプラットフォームは以下の通りです：
- [Cloudflare Pages](https://pages.cloudflare.com) - Git 連携と `nuxt build` コマンドを使用したゼロ設定
- [Vercel Edge Functions](https://vercel.com/features/edge-functions) - `nuxt build` コマンドと `NITRO_PRESET=vercel-edge` 環境変数を使用
- [Netlify Edge Functions](https://www.netlify.com/products/#netlify-edge-functions) - `nuxt build` コマンドと `NITRO_PRESET=netlify-edge` 環境変数を使用

エッジサイドレンダリングでルートルールを使用する際に **ハイブリッドレンダリング** を使用できることに注意してください。
