このガイドは ES モジュールとは何か、そして Nuxt アプリ（またはアップストリームライブラリ）を ESM と互換性を持たせる方法について説明します。

## 背景

### CommonJS モジュール

CommonJS（CJS）は Node.js によって導入された形式で、分離された JavaScript モジュール間で機能を共有することを可能にします（[詳細を読む](https://nodejs.org/api/modules.html)）。
あなたはおそらくこの構文にすでに馴染みがあるでしょう：

```js
const a = require('./a')

module.exports.a = a
```

webpack や Rollup などのバンドラーはこの構文をサポートし、ブラウザーで CommonJS で書かれたモジュールを使用することを可能にします。

### ESM 構文

大抵の場合、人々が ESM vs CJS について話すとき、彼らは[モジュール](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules)を書くための異なる構文について話しています。

```js
import a from './a'

export { a }
```

ECMAScript Modules（ESM）が標準になる前（10 年以上かかりました！）、
[webpack](https://webpack.js.org/guides/ecma-script-modules) などのツールや TypeScript などの言語でさえも、いわゆる **ESM 構文** をサポートし始めました。
しかし、実際の仕様とはいくつかの重要な違いがあります。[役立つ説明](https://hacks.mozilla.org/2018/03/es-modules-a-cartoon-deep-dive)をご覧ください。

### 「ネイティブ」ESM とは何ですか？

あなたは長い間 ESM 構文を使用してアプリを書いてきたかもしれません。結局のところ、それはブラウザーによってネイティブにサポートされており、Nuxt 2 では書いたすべてのコードを適切な形式（サーバー用は CJS、ブラウザー用は ESM）にコンパイルしていました。

パッケージにモジュールを追加するとき、状況は少し異なっていました。サンプルライブラリは CJS と ESM の両方のバージョンを公開し、どちらを使いたいかを選択させてくれるかもしれません：

```json
{
  "name": "sample-library",
  "main": "dist/sample-library.cjs.js",
  "module": "dist/sample-library.esm.js"
}
```

そのため Nuxt 2 では、バンドラー（webpack）がサーバービルド用に CJS ファイル（'main'）を取得し、クライアントビルド用に ESM ファイル（'module'）を使用していました。

しかし、最近の Node.js LTS リリースでは、Node.js 内で[ネイティブ ESM モジュールを使用](https://nodejs.org/api/esm.html)することが可能になりました。つまり Node.js 自体が ESM 構文を使用した JavaScript を処理できるということですが、デフォルトではそうしません。ESM 構文を有効にする最も一般的な 2 つの方法は：

- `package.json` 内で `"type": "module"` を設定し、`.js` 拡張子を使い続ける
- `.mjs` ファイル拡張子を使用する（推奨）

これは Nuxt Nitro で私たちが行っていることです。`.output/server/index.mjs` ファイルを出力します。これは Node.js にこのファイルをネイティブ ES モジュールとして扱うよう指示します。

### Node.js コンテキストでの有効なインポートとは何ですか？

モジュールを `require` するのではなく `import` するとき、Node.js は異なって解決します。たとえば、`sample-library` をインポートするとき、Node.js は `main` ではなく、そのライブラリの `package.json` の `exports` または `module` エントリを探します。

これは `const b = await import('sample-library')` のような動的インポートでも同様です。

Node は以下の種類のインポートをサポートしています（[ドキュメント](https://nodejs.org/api/packages.html#determining-module-system)を参照）：

1. `.mjs` で終わるファイル - これらは ESM 構文を使用することが期待されています
1. `.cjs` で終わるファイル - これらは CJS 構文を使用することが期待されています
1. `.js` で終わるファイル - これらの `package.json` に `"type": "module"` がない限り、CJS 構文を使用することが期待されています

### どのような問題が発生する可能性がありますか？

長い間、モジュール作成者は ESM 構文のビルドを作成してきましたが、`.esm.js` や `.es.js` のような慣例を使用し、それらを `package.json` の `module` フィールドに追加してきました。これまで問題になっていなかったのは、ファイル拡張子を特に気にしない webpack などのバンドラーによってのみ使用されていたからです。

しかし、Node.js ESM コンテキストで `.esm.js` ファイルを持つパッケージをインポートしようとすると、動作せず、次のようなエラーが発生します：

```bash [Terminal]
(node:22145) Warning: To load an ES module, set "type": "module" in the package.json or use the .mjs extension.
/path/to/index.js:1

export default {}
^^^^^^

SyntaxError: Unexpected token 'export'
    at wrapSafe (internal/modules/cjs/loader.js:1001:16)
    at Module._compile (internal/modules/cjs/loader.js:1049:27)
    at Object.Module._extensions..js (internal/modules/cjs/loader.js:1114:10)
    ....
    at async Object.loadESM (internal/process/esm_loader.js:68:5)
```

Node.js が CJS だと思っている ESM 構文ビルドから名前付きインポートをしている場合にも、このエラーが発生する可能性があります：

```bash [Terminal]

import { named } from 'sample-library'
         ^^^^^

CommonJS modules can always be imported via the default export, for example using:

const { named } = pkg;

    at async Object.loadESM (internal/process/esm_loader.js:68:5)
```

## ESM 問題のトラブルシューティング

これらのエラーに遇遇した場合、問題はほぼ確実にアップストリームライブラリにあります。彼らは Node によってインポートされることをサポートするために[ライブラリを修正](#library-author-guide)する必要があります。

### ライブラリのトランスパイル

その間、`build.transpile` に追加することで、Nuxt にこれらのライブラリをインポートしようとしないよう指示できます：

```ts twoslash
export default defineNuxtConfig({
  build: {
    transpile: ['sample-library']
  }
})
```

これらのライブラリによってインポートされている他のパッケージも追加する必要があることがわかるかもしれません。

### ライブラリのエイリアシング

場合によっては、ライブラリを CJS バージョンに手動でエイリアシングする必要があるかもしれません。例えば：

```ts twoslash
export default defineNuxtConfig({
  alias: {
    'sample-library': 'sample-library/dist/sample-library.cjs.js'
  }
})
```

### デフォルトエクスポート

CommonJS 形式の依存関係は、`module.exports` または `exports` を使用してデフォルトエクスポートを提供できます：

```js [node_modules/cjs-pkg/index.js]
module.exports = { test: 123 }
// or
exports.test = 123
```

このような依存関係を `require` する場合、通常はうまく動作します：

```js [test.cjs]
const pkg = require('cjs-pkg')

console.log(pkg) // { test: 123 }
```

[ネイティブ ESM モードの Node.js](https://nodejs.org/api/esm.html#interoperability-with-commonjs)、[`esModuleInterop` が有効な TypeScript](https://www.typescriptlang.org/tsconfig#esModuleInterop)、そして webpack などのバンドラーは、このようなライブラリをデフォルトインポートできるように互換性メカニズムを提供しています。
このメカニズムはしばしば「interop require default」と呼ばれます：

```js
import pkg from 'cjs-pkg'

console.log(pkg) // { test: 123 }
```

しかし、構文検出や異なるバンドル形式の複雑さのため、interop default が失敗し、次のような結果になる可能性が常にあります：

```js
import pkg from 'cjs-pkg'

console.log(pkg) // { default: { test: 123 } }
```

また、動的インポート構文を使用する場合（CJS と ESM ファイルの両方で）、常にこの状況が発生します：

```js
import('cjs-pkg').then(console.log) // [Module: null prototype] { default: { test: '123' } }
```

この場合、デフォルトエクスポートを手動で interop する必要があります：

```js
// Static import
import { default as pkg } from 'cjs-pkg'

// Dynamic import
import('cjs-pkg').then(m => m.default || m).then(console.log)
```

より複雑な状況を処理し、より安全性を確保するために、私たちは名前付きエクスポートを保持できる [mlly](https://github.com/unjs/mlly) を Nuxt で推奨し、内部で使用しています。

```js
import { interopDefault } from 'mlly'

// Assuming the shape is { default: { foo: 'bar' }, baz: 'qux' }
import myModule from 'my-module'

console.log(interopDefault(myModule)) // { foo: 'bar', baz: 'qux' }
```

## ライブラリ作成者ガイド

良いニュースは、ESM 互換性の問題を修正することは比較的簡単だということです。主なオプションは 2 つあります：

1. **ESM ファイルを `.mjs` で終わるようにリネームする。**

   _これは推奨される最も簡単なアプローチです。_ ライブラリの依存関係やビルドシステムの問題を解決する必要があるかもしれませんが、ほとんどの場合、これで問題を解決できるはずです。最大の明確さのために、CJS ファイルを `.cjs` で終わるようにリネームすることも推奨されます。

1. **ライブラリ全体を ESM のみにすることを選択する。**

   これは `package.json` で `"type": "module"` を設定し、ビルドされたライブラリが ESM 構文を使用することを確実にすることを意味します。しかし、依存関係で問題に直面する可能性があり、このアプローチはライブラリが ESM コンテキストで_のみ_消費されることを意味します。

### マイグレーション

CJS から ESM への最初のステップは、`require` の使用をすべて `import` を使用するように更新することです：

::code-group

```js [Before]
module.exports = ...

exports.hello = ...
```

```js [After]
export default ...

export const hello = ...
```

::

::code-group

```js [Before]
const myLib = require('my-lib')
```

```js [After]
import myLib from 'my-lib'
// or
const myLib = await import('my-lib').then(lib => lib.default || lib)
```

::

ESM モジュールでは、CJS とは異なり、`require`、`require.resolve`、`__filename`、`__dirname` のグローバルは利用できず、
`import()` と `import.meta.filename` で置き換える必要があります。

::code-group

```js [Before]
import { join } from 'path'

const newDir = join(__dirname, 'new-dir')
```

```js [After]
import { fileURLToPath } from 'node:url'

const newDir = fileURLToPath(new URL('./new-dir', import.meta.url))
```

::

::code-group

```js [Before]
const someFile = require.resolve('./lib/foo.js')
```

```js [After]
import { resolvePath } from 'mlly'

const someFile = await resolvePath('my-lib', { url: import.meta.url })
```

::

### ベストプラクティス

- デフォルトエクスポートよりも名前付きエクスポートを優先する。これは CJS の競合を減らすのに役立ちます。（[デフォルトエクスポート](#default-exports)セクションを参照）

- Nitro polyfill を必要とせずにブラウザーや Edge Worker でライブラリを使用可能にするために、Node.js 組み込みや CommonJS 、Node.js 専用の依存関係にできる限り依存しないようにする。

- 条件付きエクスポートで新しい `exports` フィールドを使用する。（[詳細を読む](https://nodejs.org/api/packages.html#conditional-exports)）。

```json
{
  "exports": {
    ".": {
      "import": "./dist/mymodule.mjs"
    }
  }
}
```
