Nuxt の [設定](/docs/api/nuxt-config)と[フック](/docs/guide/going-further/hooks)システムにより、Nuxt のあらゆる側面をカスタマイズし、必要な統合（Vue プラグイン、CMS、サーバールート、コンポーネント、ロギングなど）を追加することが可能です。

**Nuxt モジュール**は、`nuxt dev` を使用して開発モードで Nuxt を起動するか、`nuxt build` でプロダクション用にプロジェクトをビルドする際に順次実行される関数です。
モジュールを使用することで、プロジェクトに不要な定型コードを追加したり、Nuxt 自体に変更を加えたりすることなく、カスタムソリューションを npm パッケージとしてカプセル化し、適切にテストし、共有することができます。

## クイックスタート

Nuxt モジュールの開始には、[スターターテンプレート](https://github.com/nuxt/starter/tree/module)の使用をお勧めします：

::code-group{sync="pm"}

```bash [npm]
npm create nuxt -- -t module my-module
```

```bash [yarn]
yarn create nuxt -t module my-module
```

```bash [pnpm]
pnpm create nuxt -t module my-module
```

```bash [bun]
bun create nuxt -t module my-module
```
::

これにより、モジュールの開発と公開に必要なすべての定型コードを含む `my-module` プロジェクトが作成されます。

**次のステップ：**

1. お好みの IDE で `my-module` を開く
2. お好みのパッケージマネージャーを使用して依存関係をインストールする
3. `npm run dev:prepare` を使用して開発用のローカルファイルを準備する
4. このドキュメントに従って Nuxt モジュールについてさらに学ぶ

#### 開発方法

モジュールのソースコードは `src` ディレクトリ内にありますが、ほとんどの場合、モジュールを開発するには Nuxt アプリケーションが必要です。それが `playground` ディレクトリの役割です。これは、あなたのモジュールと動作するように既に設定された、いじることができる Nuxt アプリケーションです。

playground は通常の Nuxt アプリケーションと同様に操作できます。

- `npm run dev` で開発サーバーを起動します。`src` ディレクトリでモジュールに変更を加えると、自動的にリロードされます
- `npm run dev:build` でビルドします

::note
他のすべての `nuxt` コマンドは `playground` ディレクトリに対して使用できます（例：`nuxt <COMMAND> playground`）。便利のため、`package.json` 内でそれらを参照する追加の `dev:*` スクリプトを自由に宣言してください。
::

#### テスト方法

モジュールスターターには基本的なテストスイートが付属しています：

- [ESLint](https://eslint.org) によるリンター、`npm run lint` で実行します
- [Vitest](https://vitest.dev) によるテストランナー、`npm run test` または `npm run test:watch` で実行します

::tip
ニーズに合わせて、このデフォルトのテスト戦略を自由に拡張してください。
::

#### ビルド方法

Nuxt モジュールには [`@nuxt/module-builder`](https://github.com/nuxt/module-builder#readme) によって提供される独自のビルダーが付属しています。このビルダーはあなた側での設定を必要とせず、TypeScript をサポートし、他の Nuxt アプリケーションに配布するためにアセットが適切にバンドルされることを保証します。

`npm run prepack` を実行してモジュールをビルドできます。

::tip
モジュールのビルドは場合によっては有用ですが、ほとんどの場合、自分でビルドする必要はありません：開発中は `playground` が処理し、公開時はリリーススクリプトもカバーします。
::

#### 公開方法

::important
モジュールを npm に公開する前に、[npmjs.com](https://www.npmjs.com) アカウントがあることと、`npm login` でローカルに認証されていることを確認してください。
::

バージョンをアップしてから `npm publish` コマンドを使用してモジュールを公開することもできますが、モジュールスターターには、動作するバージョンのモジュールを npm に確実に公開するためのリリーススクリプトが含まれています。

リリーススクリプトを使用するには、まずすべての変更をコミットし（[Conventional Commits](https://www.conventionalcommits.org) に従うことをお勧めします。自動バージョンアップとチェンジログ更新の利点を得られます）、その後 `npm run release` でリリーススクリプトを実行します。

リリーススクリプトを実行すると、以下が実行されます：

- 最初に、テストスイートを実行します：
  - リンターの実行（`npm run lint`）
  - ユニット、統合、および e2e テストの実行（`npm run test`）
  - モジュールのビルド（`npm run prepack`）
- その後、テストスイートが正常に完了した場合、モジュールの公開を進めます：
  - Conventional Commits に従ってモジュールバージョンをアップし、チェンジログを生成します
  - モジュールを npm に公開します（この目的のため、更新されたバージョン番号が公開されるアーティファクトに反映されるように、モジュールが再度ビルドされます）
  - 新しく公開されたバージョンを表す git タグを git remote origin にプッシュします

::tip
他のスクリプトと同様に、ニーズに合わせて `package.json` のデフォルトの `release` スクリプトを自由に調整してください。
::

## モジュール開発

Nuxt モジュールは、Nuxt アプリケーションをほぼあらゆる方法で変更することができる多様で強力な API とパターンを提供しています。このセクションでは、それらを活用する方法を学びます。

### モジュールの構造

Nuxt モジュールには 2 つの種類があります：

- npm で配布される公開モジュール - [Nuxt ウェブサイト](/modules)でコミュニティモジュールのリストを見ることができます。
- Nuxt プロジェクト内に存在する「ローカル」モジュール - [Nuxt config にインライン化](/docs/api/nuxt-config#modules)されるか、[`modules` ディレクトリ](/docs/guide/directory-structure/modules)の一部として存在します。

どちらの場合でも、その構造は似ています。

#### モジュール定義

::note
スターターを使用する場合、モジュール定義は `src/module.ts` で利用できます。
::

モジュール定義は、モジュールのエントリーポイントです。Nuxt 設定内でモジュールが参照されたときに、Nuxt によって読み込まれるものです。

低レベルでは、Nuxt モジュール定義は、インラインユーザーオプションと Nuxt とやり取りするための `nuxt` オブジェクトを受け取るシンプルで、潜在的に非同期な関数です。

```ts
export default function (inlineOptions, nuxt) {
  // You can do whatever you like here..
  console.log(inlineOptions.token) // `123`
  console.log(nuxt.options.dev) // `true` or `false`
  nuxt.hook('ready', async nuxt => {
    console.log('Nuxt is ready')
  })
}
```

[Nuxt Kit](/docs/guide/going-further/kit) が提供する高レベルな `defineNuxtModule` ヘルパーを使用して、この関数の型ヒントサポートを得ることができます。

```ts
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule((options, nuxt) => {
  nuxt.hook('pages:extend', pages => {
    console.log(`Discovered ${pages.length} pages`)
  })
})
```

しかし、この低レベルな関数定義の使用は**推奨しません**。代わりに、モジュールを定義するには、特に npm に公開する場合は、モジュールを識別するための `meta` プロパティを持つオブジェクト構文の使用を**推奨します**。

このヘルパーは、モジュールに必要な多くの一般的なパターンを実装することで Nuxt モジュールの作成をより簡単にし、将来の互換性を保証し、モジュール作成者とユーザーの両方の体験を向上させます。

```ts
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: {
    // Usually the npm package name of your module
    name: '@nuxtjs/example',
    // The key in `nuxt.config` that holds your module options
    configKey: 'sample',
    // Compatibility constraints
    compatibility: {
      // Semver version of supported nuxt versions
      nuxt: '>=3.0.0'
    }
  },
  // Default configuration options for your module, can also be a function returning those
  defaults: {},
  // Shorthand sugar to register Nuxt hooks
  hooks: {},
  // The function holding your module logic, it can be asynchronous
  setup(moduleOptions, nuxt) {
    // ...
  }
})
```

最終的に `defineNuxtModule` は、低レベルな `(inlineOptions, nuxt)` モジュールシグネチャを持つラッパー関数を返します。このラッパー関数は、`setup` 関数を呼び出す前にデフォルトとその他の必要なステップを適用します：

- モジュールオプションを自動的にマージするための `defaults` と `meta.configKey` のサポート
- 型ヒントと自動型推論
- 基本的な Nuxt 2 互換性のためのシムを追加
- `meta.name` または `meta.configKey` から計算されたユニークキーを使用してモジュールが一度だけインストールされることを保証
- Nuxt フックの自動登録
- モジュールメタに基づく互換性問題の自動チェック
- Nuxt の内部使用のための `getOptions` と `getMeta` の公開
- モジュールが最新バージョンの `@nuxt/kit` の `defineNuxtModule` を使用している限り、後方および前方互換性の保証
- モジュールビルダーツールとの統合

#### ランタイムディレクトリ

::note
スターターを使用する場合、ランタイムディレクトリは `src/runtime` で利用できます。
::

モジュールは、Nuxt 設定のすべてと同様に、アプリケーションランタイムには含まれません。しかし、モジュールがインストールされたアプリケーションにランタイムコードを提供したり、注入したりしたい場合があります。それがランタイムディレクトリで可能になることです。

ランタイムディレクトリ内では、Nuxt App に関連するあらゆる種類のアセットを提供できます：
- Vue コンポーネント
- Composables
- [Nuxt プラグイン](/docs/guide/directory-structure/plugins)

[サーバーエンジン](/docs/guide/concepts/server-engine)の Nitro には：
- API ルート
- ミドルウェア
- Nitro プラグイン

または、ユーザーの Nuxt アプリケーションに注入したいその他のあらゆる種類のアセット：
- スタイルシート
- 3D モデル
- 画像
- など

その後、[モジュール定義](#module-definition)からアプリケーション内にそれらすべてのアセットを注入できるようになります。

::tip
アセットの注入について詳しくは、[レシピセクション](#recipes)をご覧ください。
::

::warning
公開されたモジュールは、ランタイムディレクトリ内のアセットに対して自動インポートを活用できません。代わりに、`#imports` などから明示的にインポートする必要があります。
:br :br
実際、パフォーマンス上の理由から、`node_modules`（公開されたモジュールが最終的に配置される場所）内のファイルに対しては自動インポートは有効になりません。
::

### ツール

モジュールには、開発を支援するファーストパーティツールのセットが付属しています。

#### `@nuxt/module-builder`

[Nuxt Module Builder](https://github.com/nuxt/module-builder#readme) は、モジュールをビルドして配布するためのすべての重い作業を処理するゼロ設定のビルドツールです。モジュールのビルドアーティファクトが Nuxt アプリケーションと適切に互換性があることを保証します。

#### `@nuxt/kit`

[Nuxt Kit](/docs/guide/going-further/kit) は、モジュールが Nuxt アプリケーションと相互作用するのを助ける Composable ユーティリティを提供します。モジュールのより良い互換性とコードの可読性を確保するために、可能な限り手動の代替手段よりも Nuxt Kit ユーティリティを使用することをお勧めします。

:read-more{to="/docs/guide/going-further/kit"}

#### `@nuxt/test-utils`

[Nuxt Test Utils](/docs/getting-started/testing) は、モジュールテスト内で Nuxt アプリケーションをセットアップして実行するのに役立つユーティリティのコレクションです。

### レシピ

モジュール作成に使用される一般的なパターンをここで見つけてください。

#### Nuxt 配置の変更

Nuxt 配置はモジュールによって読み取りや変更ができます。以下は実験的機能を有効にするモジュールの例です。

```js
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    // We create the `experimental` object if it doesn't exist yet
    nuxt.options.experimental ||= {}
    nuxt.options.experimental.componentIslands = true
  }
})
```

より複雑な配置の変更を処理する必要がある場合は、[defu](https://github.com/unjs/defu) の使用を検討してください。

::tip{icon="i-lucide-video" to="https://vueschool.io/lessons/extending-and-altering-nuxt-configuration-and-options?friend=nuxt" target="_blank"}
Nuxt 配置の変更についての Vue School 動画を視聴してください。
::

#### ランタイムへのオプション公開

モジュールはアプリケーションランタイムの一部ではないため、そのオプションも同様です。しかし、多くの場合、ランタイムコード内でこれらのモジュールオプションの一部にアクセスする必要があるかもしれません。Nuxt の [`runtimeConfig`](/docs/api/nuxt-config#runtimeconfig) を使用して必要な設定を公開することをお勧めします。

<!-- TODO: Update after #18466 (or equivalent) -->

```js
import { defineNuxtModule } from '@nuxt/kit'
import { defu } from 'defu'

export default defineNuxtModule({
  setup (options, nuxt) {
    nuxt.options.runtimeConfig.public.myModule = defu(nuxt.options.runtimeConfig.public.myModule, {
      foo: options.foo
    })
  }
})
```

ユーザーが提供するパブリックランタイム配置を上書きするのではなく拡張するために、[`defu`](https://github.com/unjs/defu) を使用していることに注意してください。

その後、他のランタイム配置と同じように、プラグイン、コンポーネント、アプリケーションでモジュールオプションにアクセスできます：

```js
const options = useRuntimeConfig().public.myModule
```

::warning
プライベート API キーなどの機密なモジュール配置をパブリックランタイム配置で公開しないよう注意してください。それらはパブリックバンドルに含まれてしまいます。
::

#### `addPlugin` でプラグインを注入

プラグインは、モジュールがランタイムロジックを追加する一般的な方法です。`addPlugin` ユーティリティを使用して、モジュールからそれらを登録できます。

```js
import { defineNuxtModule, addPlugin, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    // Create resolver to resolve relative paths
    const resolver = createResolver(import.meta.url)

    addPlugin(resolver.resolve('./runtime/plugin'))
  }
})
```

:read-more{to="/docs/guide/going-further/kit"}

#### `addComponent` で Vue コンポーネントを注入

モジュールが Vue コンポーネントを提供する必要がある場合、`addComponent` ユーティリティを使用して、Nuxt が解決するための自動インポートとしてそれらを追加できます。

```js
import { defineNuxtModule, addComponent } from '@nuxt/kit'

export default defineNuxtModule({
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)

    // From the runtime directory
    addComponent({
      name: 'MySuperComponent', // name of the component to be used in vue templates
      export: 'MySuperComponent', // (optional) if the component is a named (rather than default) export
      filePath: resolver.resolve('runtime/components/MySuperComponent.vue')
    })

    // From a library
    addComponent({
      name: 'MyAwesomeComponent', // name of the component to be used in vue templates
      export: 'MyAwesomeComponent', // (optional) if the component is a named (rather than default) export
      filePath: '@vue/awesome-components'
    })
  }
})
```

または、`addComponentsDir` を使用してディレクトリ全体を追加することもできます。

```ts
import { defineNuxtModule, addComponentsDir } from '@nuxt/kit'

export default defineNuxtModule({
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)

    addComponentsDir({
      path: resolver.resolve('runtime/components')
    })
  }
})
```

#### `addImports` と `addImportsDir` で Composables を注入

モジュールが Composables を提供する必要がある場合、`addImports` ユーティリティを使用して、Nuxt が解決するための自動インポートとしてそれらを追加できます。

```ts
import { defineNuxtModule, addImports, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)

    addImports({
      name: 'useComposable', // name of the composable to be used
      as: 'useComposable',
      from: resolver.resolve('runtime/composables/useComposable') // path of composable
    })
  }
})
```

または、`addImportsDir` を使用してディレクトリ全体を追加することもできます。

```ts
import { defineNuxtModule, addImportsDir, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)

    addImportsDir(resolver.resolve('runtime/composables'))
  }
})
```

#### `addServerHandler` でサーバールートを注入

```ts
import { defineNuxtModule, addServerHandler, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)

    addServerHandler({
      route: '/api/hello',
      handler: resolver.resolve('./runtime/server/api/hello/index.get')
    })
  }
})
```

ダイナミックサーバールートを追加することもできます：

```ts
import { defineNuxtModule, addServerHandler, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)

    addServerHandler({
      route: '/api/hello/:name',
      handler: resolver.resolve('./runtime/server/api/hello/[name].get')
    })
  }
})
```

#### その他のアセットの注入

モジュールがその他の種類のアセットを提供する必要がある場合、それらも注入できます。以下は、Nuxt の `css` 配列を通じてスタイルシートを注入するシンプルなモジュールの例です。

```js
import { defineNuxtModule, addPlugin, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    const resolver = createResolver(import.meta.url)

    nuxt.options.css.push(resolver.resolve('./runtime/style.css'))
  }
})
```

さらに高度な例として、[Nitro](/docs/guide/concepts/server-engine) の `publicAssets` オプションを通じてアセットのフォルダーを公開する例：

```js
import { defineNuxtModule, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    const resolver = createResolver(import.meta.url)

    nuxt.hook('nitro:config', async (nitroConfig) => {
      nitroConfig.publicAssets ||= []
      nitroConfig.publicAssets.push({
        dir: resolver.resolve('./runtime/public'),
        maxAge: 60 * 60 * 24 * 365 // 1 year
      })
    })
  }
})
```

#### モジュール内で他のモジュールを使用

モジュールが他のモジュールに依存している場合、Nuxt Kit の `installModule` ユーティリティを使用してそれらを追加できます。たとえば、モジュールで Nuxt Tailwind を使用したい場合、以下のように追加できます：

```ts
import { defineNuxtModule, createResolver, installModule } from '@nuxt/kit'

export default defineNuxtModule<ModuleOptions>({
  async setup (options, nuxt) {
    const resolver = createResolver(import.meta.url)

    // We can inject our CSS file which includes Tailwind's directives
    nuxt.options.css.push(resolver.resolve('./runtime/assets/styles.css'))

    await installModule('@nuxtjs/tailwindcss', {
      // module configuration
      exposeConfig: true,
      config: {
        darkMode: 'class',
        content: {
          files: [
            resolver.resolve('./runtime/components/**/*.{vue,mjs,ts}'),
            resolver.resolve('./runtime/*.{mjs,js,ts}')
          ]
        }
      }
    })
  }
})
```

#### フックの使用

[ライフサイクルフック](/docs/guide/going-further/hooks)を使用すると、Nuxt のほぼあらゆる側面を拡張できます。モジュールは、プログラム的に、または定義内の `hooks` マップを通じてそれらにフックできます。

```js
import { defineNuxtModule, addPlugin, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  // Hook to the `app:error` hook through the `hooks` map
  hooks: {
    'app:error': (err) => {
      console.info(`This error happened: ${err}`);
    }
  },
  setup (options, nuxt) {
    // Programmatically hook to the `pages:extend` hook
    nuxt.hook('pages:extend', (pages) => {
      console.info(`Discovered ${pages.length} pages`);
    })
  }
})
```

**モジュールのクリーンアップ**
:br
:br
モジュールがウォッチャーを開いたり、処理したり、開始したりする場合、Nuxt ライフサイクルが終了したときにそれを閉じる必要があります。このために `close` フックが利用できます。

```ts
import { defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    nuxt.hook('close', async nuxt => {
      // ここにカスタムコードを記述
    })
  }
})
```

#### テンプレート/仮想ファイルの追加

ユーザーのアプリにインポートできる仮想ファイルを追加する必要がある場合、`addTemplate` ユーティリティを使用できます。

```ts
import { defineNuxtModule, addTemplate } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    // The file is added to Nuxt's internal virtual file system and can be imported from '#build/my-module-feature.mjs'
    addTemplate({
      filename: 'my-module-feature.mjs',
      getContents: () => 'export const myModuleFeature = () => "hello world !"'
    })
  }
})
```

サーバーでは、代わりに `addServerTemplate` ユーティリティを使用する必要があります。

```ts
import { defineNuxtModule, addServerTemplate } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    // The file is added to Nitro's virtual file system and can be imported in the server code from 'my-server-module.mjs'
    addServerTemplate({
      filename: 'my-server-module.mjs',
      getContents: () => 'export const myServerModule = () => "hello world !"'
    })
  }
})
```

#### 型宣言の追加

ユーザーのプロジェクトに型宣言を追加したい場合もあります（たとえば、Nuxt インターフェースを拡張したり、独自のグローバル型を提供したりするために）。
このために、Nuxt はテンプレートをディスクに書き込み、
生成された `nuxt.d.ts` ファイルにその参照を追加する `addTypeTemplate` ユーティリティを提供しています。

モジュールが Nuxt で処理される型を拡張する必要がある場合、`addTypeTemplate` を使用してこの操作を実行できます：

```js
import { defineNuxtModule, addTemplate, addTypeTemplate } from '@nuxt/kit'

export default defineNuxtModule({
  setup (options, nuxt) {
    addTypeTemplate({
      filename: 'types/my-module.d.ts',
      getContents: () => `// Generated by my-module
        interface MyModuleNitroRules {
          myModule?: { foo: 'bar' }
        }
        declare module 'nitropack/types' {
          interface NitroRouteRules extends MyModuleNitroRules {}
          interface NitroRouteConfig extends MyModuleNitroRules {}
        }
        export {}`
    })
  }
})
```

より細かい制御が必要な場合は、`prepare:types` フックを使用して、型を注入するコールバックを登録できます。

```ts
const template = addTemplate({ /* template options */ })
nuxt.hook('prepare:types', ({ references }) => {
  references.push({ path: template.dst })
})
```

##### テンプレートの更新

テンプレート/仮想ファイルを更新する必要がある場合、`updateTemplates` ユーティリティを次のように活用できます：

```ts
nuxt.hook('builder:watch', async (event, path) => {
  if (path.includes('my-module-feature.config')) {
    // This will reload the template that you registered
    updateTemplates({ filter: t => t.filename === 'my-module-feature.mjs' })
  }
})
```

### テスト

テストは、さまざまなセットアップでモジュールが期待通りに動作することを保証するのに役立ちます。このセクションでは、モジュールに対してさまざまな種類のテストを実行する方法を説明します。

#### End to End

[Nuxt Test Utils](/docs/getting-started/testing) は、モジュールを End to End でテストするのに役立つ選択肢のライブラリです。以下は、それを使用したワークフローです：

1. `test/fixtures/*` 内に「フィクスチャ」として使用される Nuxt アプリケーションを作成します
2. テストファイル内でこのフィクスチャで Nuxt をセットアップします
3. `@nuxt/test-utils` のユーティリティを使用してフィクスチャと相互作用します（例：ページのフェッチ）
4. このフィクスチャに関連するチェックを実行します（例：「HTML に ... が含まれている」）
5. 繰り返します

実際には、フィクスチャは次のようになります：

```js [test/fixtures/ssr/nuxt.config.ts]
// 1. Create a Nuxt application to be used as a "fixture"
import MyModule from '../../../src/module'

export default defineNuxtConfig({
  ssr: true,
  modules: [
    MyModule
  ]
})
```

そしてそのテストは次のようになります：

```js [test/rendering.ts]
import { describe, it, expect } from 'vitest'
import { fileURLToPath } from 'node:url'
import { setup, $fetch } from '@nuxt/test-utils/e2e'

describe('ssr', async () => {
  // 2. Setup Nuxt with this fixture inside your test file
  await setup({
    rootDir: fileURLToPath(new URL('./fixtures/ssr', import.meta.url)),
  })

  it('renders the index page', async () => {
    // 3. Interact with the fixture using utilities from `@nuxt/test-utils`
    const html = await $fetch('/')

    // 4. Perform checks related to this fixture
    expect(html).toContain('<div>ssr</div>')
  })
})

// 5. Repeat
describe('csr', async () => { /* ... */ })
```

::tip
そのようなワークフローの例は[モジュールスターター](https://github.com/nuxt/starter/blob/module/test/basic.test.ts)で利用できます。
::

#### Playground および外部での手動 QA

モジュールを開発する際にテストするための playground Nuxt アプリケーションを持つことは非常に有用です。[モジュールスターターはその目的のためにひとつを統合しています](#開発方法)。

モジュールを他の Nuxt アプリケーション（モジュールリポジトリの一部ではないアプリケーション）でローカルにテストできます。それを行うには、[`npm pack`](https://docs.npmjs.com/cli/commands/npm-pack) コマンド、またはお使いのパッケージマネージャーの同等のコマンドを使用して、モジュールから tarball を作成できます。その後、テストプロジェクトで、`package.json` パッケージにモジュールを `"my-module": "file:/path/to/tarball.tgz"` として追加できます。

その後、通常のプロジェクトと同じように `my-module` を参照できるようになります。

### ベストプラクティス

大きな力には大きな責任が伴います。モジュールは強力ですが、アプリケーションのパフォーマンスと開発者体験を良好に保つために、モジュールを作成する際に心に留めておくべきベストプラクティスをいくつか紹介します。

#### 非同期モジュール

これまで見てきたように、Nuxt モジュールは非同期にできます。たとえば、API をフェッチしたり、非同期関数を呼び出したりする必要があるモジュールを開発したい場合があります。

しかし、Nuxt は次のモジュールに進んで開発サーバー、ビルドプロセスなどを開始する前に、モジュールのセットアップを待つため、非同期動作には注意が必要です。時間のかかるロジックは Nuxt フックに延期することをお勧めします。

::warning
モジュールのセットアップに **1 秒**以上かかる場合、Nuxt はそれについて警告を発行します。
::

#### 公開インターフェースには必ず接頭辞を付ける

Nuxt モジュールは、他のモジュールや内部との競合を避けるために、公開される設定、プラグイン、API、Composable、またはコンポーネントに明示的な接頭辞を提供する必要があります。

理想的には、モジュール名で接頭辞を付ける必要があります（たとえば、モジュールが `nuxt-foo` と呼ばれる場合、`<FooButton>` と `useFooBar()` を公開し、`<Button>` や `useBar()` では**なく**）。

#### TypeScript フレンドリーにする

Nuxt は、最高の開発者体験のためにファーストクラスの TypeScript 統合を持っています。

型を公開し、TypeScript を使用してモジュールを開発することは、TypeScript を直接使用していない場合でもユーザーにとって有益です。

#### CommonJS 構文を避ける

Nuxt はネイティブ ESM に依存しています。詳細については [Native ES Modules](/docs/guide/concepts/esm) をお読みください。

#### モジュールの使用方法を文書化する

readme ファイルでモジュールの使用方法を文書化することを検討してください：

- なぜこのモジュールを使用するのか？
- このモジュールをどのように使用するのか？
- このモジュールは何をするのか？

統合ウェブサイトやドキュメントにリンクすることは常に良いアイデアです。

#### StackBlitz デモまたはボイラープレートを提供する

モジュールと [StackBlitz](https://nuxt.new/s/v3) で最小限の再現を作成し、モジュール readme に追加することは良い習慣です。

これは、モジュールの潜在的なユーザーにモジュールを実験する迅速で簡単な方法を提供するだけでなく、問題に遇遇したときにあなたに送信できる最小限の再現を構築する簡単な方法でもあります。

#### 特定の Nuxt バージョンで宣伝しない

Nuxt、Nuxt Kit、およびその他の新しいツールは、前方および後方互換性を念頭に置いて作られています。

エコシステムの断片化を避けるために、「X for Nuxt 3」の代わりに「X for Nuxt」を使用し、Nuxt バージョン制約を設定するには `meta.compatibility` を使用することをお勧めします。

#### スターターのデフォルトを使用する

モジュールスターターには、デフォルトのツールや設定のセット（ESLint 設定など）が付属しています。モジュールをオープンソースすることを計画している場合、これらのデフォルトを使用することで、モジュールが他の[コミュニティモジュール](/modules)と一貫したコーディングスタイルを共有し、他の人が貢献しやすくなることが保証されます。

### モジュールタイプ

**公式モジュール**は、`@nuxt/` で接頭辞（スコープ）が付いたモジュールです（例：[`@nuxt/content`](https://content.nuxtjs.org)）。これらは Nuxt チームによって作成され、積極的にメンテナンスされています。フレームワークと同様に、コミュニティからの貢献は、それらをより良くするために大歓迎です！

**コミュニティモジュール**は、`@nuxtjs/` で接頭辞（スコープ）が付いたモジュールです（例：[`@nuxtjs/tailwindcss`](https://tailwindcss.nuxtjs.org)）。これらはコミュニティメンバーによって作成・保守された実証済みのモジュールです。再び、誰でも貢献を歓迎します。

**サードパーティおよびその他のコミュニティモジュール**は、（多くの場合）`nuxt-` で接頭辞が付いたモジュールです。誰でも作成でき、この接頭辞を使用することで、これらのモジュールを npm で発見できるようになります。これはアイデアを下書きして試すのに最適な開始点です！

**プライベートまたは個人モジュール**は、あなた自身のユースケースや会社のために作成されたモジュールです。Nuxt で動作するために命名ルールに従う必要はなく、npm 組織下でスコープされることがよくあります（例：`@my-company/nuxt-auth`）

### コミュニティモジュールのリスト投稿

どのコミュニティモジュールも[モジュールリスト](/modules)に投稿することを歓迎します。投稿するには、[nuxt/modules リポジトリで issue を開いてください](https://github.com/nuxt/modules/issues/new?template=module_request.yml)。Nuxt チームは、投稿前にベストプラクティスを適用するお手伝いをすることができます。

### `nuxt-modules` と `@nuxtjs/` への参加

モジュールを [nuxt-modules](https://github.com/nuxt-modules) に移動することで、常に他の人が支援し、このようにして力を合わせて一つの完璧なソリューションを作ることができます。

既に公開されていて動作しているモジュールがあり、それを `nuxt-modules` に移管したい場合は、[nuxt/modules で issue を開いてください](https://github.com/nuxt/modules/issues/new)。

`nuxt-modules` に参加することで、コミュニティモジュールを `@nuxtjs/` スコープ下で名前変更し、そのドキュメントのためにサブドメイン（例：`my-module.nuxtjs.org`）を提供できます。
