Nuxt の実験的機能は Nuxt 設定ファイルで有効にすることができます。

内部的に、Nuxt は `@nuxt/schema` を使用してこれらの実験的機能を定義しています。詳細については、[API ドキュメント](/docs/api/configuration/nuxt-config#experimental)または[ソースコード](https://github.com/nuxt/nuxt/blob/main/packages/schema/src/config/experimental.ts)を参照してください。

::note
これらの機能は実験的なものであり、将来削除または変更される可能性があることに注意してください。
::

## asyncContext

Nuxt と Nitro でネストされたコンポーザブルがネイティブ非同期コンテキストにアクセスできるようにします。これにより、非同期コンポーザブル内でコンポーザブルを使用することが可能になり、`Nuxt instance is unavailable` エラーが発生する可能性を減らすことができます。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncContext: true
  }
})
```

::read-more{icon="i-simple-icons-github" to="https://github.com/nuxt/nuxt/pull/20918" target="_blank"}
GitHub プルリクエストで詳細な説明を参照してください。
::

## emitRouteChunkError

vite/webpack チャンクの読み込みでエラーが発生した際に `app:chunkError` フックを発行します。デフォルトの動作は、チャンクの読み込みに失敗した場合に新しいルートへのナビゲーション時に新しいルートのリロードを実行することです。

これを `'automatic-immediate'` に設定すると、Nuxt はナビゲーションを待つ代わりに現在のルートを即座にリロードします。これは、ナビゲーションによってトリガーされないチャンクエラー、例えば Nuxt アプリが[レイジーコンポーネント](/docs/guide/directory-structure/components#dynamic-imports)の読み込みに失敗した場合に有用です。この動作の潜在的な欠点は、例えばアプリがエラーの原因となったチャンクを必要としない場合の望ましくないリロードです。

これを `false` に設定して自動処理を無効にするか、`manual` に設定してチャンクエラーを手動で処理できます。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    emitRouteChunkError: 'automatic' // または 'automatic-immediate'、'manual'、false
  }
})
```

## restoreState

チャンクエラーまたは手動の [`reloadNuxtApp()`](/docs/api/utils/reload-nuxt-app) 呼び出し後にページをリロードする際に、`sessionStorage` から Nuxt アプリの状態を復元できるようにします。

ハイドレーションエラーを避けるため、Vue アプリがマウントされた後にのみ適用されるため、初期読み込み時にちらつきが発生する可能性があります。

::important
これを有効にする前に慎重に検討してください。予期しない動作を引き起こす可能性があり、
自動生成されたキーはビルド間で一致しない可能性があるため、[`useState`](/docs/api/composables/use-state) に明示的なキーを提供することを検討してください。
::

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    restoreState: true
  }
})
```

## watcher

Nuxt の監視サービスとして使用される代替ウォッチャーを設定します。

Nuxt はデフォルトで `chokidar-granular` を使用し、監視から除外される
（`node_modules` や `.git` などの）トップレベルディレクトリを無視します。

これを `parcel` に設定して `@parcel/watcher` を使用することで、
大規模プロジェクトや Windows プラットフォームでのパフォーマンスが向上する場合があります。

また、これを `chokidar` に設定してソースディレクトリ内のすべてのファイルを監視することもできます。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    watcher: 'chokidar-granular' // 'chokidar' または 'parcel' もオプションです
  }
})
```

## sharedPrerenderData

この機能を有効にすると、プリレンダリングされたページ間でペイロード *データ* が自動的に共有されます。これにより、
`useAsyncData` や `useFetch` を使用し、異なるページで同じデータを取得するサイトをプリレンダリングする際に
大幅なパフォーマンス向上をもたらすことができます。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    sharedPrerenderData: true
  }
})
```

:video-accordion{title="Alexander Lichter による実験的な sharedPrerenderData についての動画を視聴する" videoId="1jUupYHVvrU"}

この機能を有効にする際は、データの一意キーが常に同じデータに解決できることを確認することが特に重要です。
例えば、特定のページに関連するデータを取得するために `useAsyncData` を使用している場合は、
そのデータに一意に一致するキーを提供する必要があります。
（`useFetch` はこれを自動的に行います。）

```ts
// これは動的ページ（例：`[slug].vue`）では安全ではありません。ルートスラッグが取得データに違いをもたらしますが、
// キーに反映されていないため、Nuxt はそれを知ることができません。
const route = useRoute()
const { data } = await useAsyncData(async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
// 代わりに、取得したデータを一意に識別するキーを使用する必要があります。
const { data } = await useAsyncData(route.params.slug, async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
```

## scanPageMeta

このオプションにより、`definePageMeta` で定義されたルートメタデータの一部（具体的には `alias`、`name`、`path`、`redirect`、`props`、`middleware`）をビルド時にモジュールに公開できます。

これは変数や条件付き代入ではなく、静的または文字列/配列でのみ動作します。詳細とコンテキストについては、[元の課題](https://github.com/nuxt/nuxt/issues/24770)を参照してください。

`pages:extend` ですべてのルートが登録された後にのみページメタデータをスキャンすることも可能です。その後、別のフック `pages:resolved` が呼び出されます。この動作を有効にするには、`scanPageMeta: 'after-resolve'` を設定します。

プロジェクトで問題が発生する場合は、この機能を無効にできます。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    scanPageMeta: false
  }
})
```

## buildCache

設定ファイルとソースファイルのハッシュに基づいて Nuxt ビルドアーティファクトをキャッシュします。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    buildCache: true
  }
})
```

有効にすると、以下のファイルの変更でフルリビルドがトリガーされます：

```bash [ディレクトリ構造]
.nuxtrc
.npmrc
package.json
package-lock.json
yarn.lock
pnpm-lock.yaml
tsconfig.json
bun.lock
bun.lockb
```

さらに、`srcDir` 内のファイルの変更は Vue クライアント/サーバーバンドルのリビルドをトリガーします。Nitro は常にリビルドされます（ただし、Nitro がキャッシュ可能なアーティファクトとそれらのハッシュを通知できるようにする作業が進行中です）。

::note
最大10個のキャッシュ tar ボールが保持されます。
::

## extraPageMetaExtractionKeys

`definePageMeta()` マクロは、ページに関するビルド時メタを収集する便利な方法です。Nuxt 自体は、リダイレクト、ページエイリアス、カスタムパスなどの内部機能を強化するために使用されるサポートキーの設定リストを提供します。

このオプションにより、`scanPageMeta` を使用する際にページメタデータから抽出する追加のキーを渡すことができます。

```vue
<script lang="ts" setup>
definePageMeta({
  foo: 'bar'
})
</script>
```

```ts
export default defineNuxtConfig({
  experimental: {
    extraPageMetaExtractionKeys: ['foo'],
  },
  hooks: {
    'pages:resolved' (ctx) {
      // ✅ foo が利用可能
    },
  },
})
```

これにより、モジュールはビルドコンテキストでページメタデータから追加のメタデータにアクセスできます。モジュール内でこれを使用している場合は、[キーで `NuxtPage` 型を拡張する](/docs/guide/directory-structure/pages#typing-custom-metadata)ことも推奨されます。

## normalizeComponentNames

自動生成される Vue コンポーネント名が、
コンポーネントを自動インポートする際に使用する完全なコンポーネント名と一致することを保証します。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizeComponentNames: true
  }
})
```

デフォルトでは、手動で設定していない場合、
Vue はコンポーネントのファイル名と一致するコンポーネント名を割り当てます。

```bash [ディレクトリ構造]
├─ components/
├─── SomeFolder/
├───── MyComponent.vue
```

この場合、Vue が認識するコンポーネント名は `MyComponent` になります。`<KeepAlive>` で使用したり、Vue DevTools で識別したりする場合は、このコンポーネントを使用する必要があります。

しかし、自動インポートするためには、`SomeFolderMyComponent` を使用する必要があります。

`experimental.normalizeComponentNames` を設定することで、これら2つの値が一致し、Vue は Nuxt のコンポーネント命名パターンに一致するコンポーネント名を生成します。

## spaLoadingTemplateLocation

クライアント専用ページ（`ssr: false` で）をレンダリングする際に、オプションで読み込み画面（`~/spa-loading-template.html` から）をレンダリングします。

これを `within` に設定すると、次のようにレンダリングされます：

```html
<div id="__nuxt">

</div>
```

または、`body` に設定して Nuxt アプリルートと並行してテンプレートをレンダリングできます：

```html
<div id="__nuxt"></div>

```

これにより、クライアント専用ページをハイドレートする際の白い点滅を避けることができます。

## decorators

このオプションは、[esbuild](https://github.com/evanw/esbuild/releases/tag/v0.21.3) によって支援される、Nuxt/Nitro アプリ全体でデコレーター構文を有効にします。

長い間、TypeScript は `compilerOptions.experimentalDecorators` を介してデコレーターをサポートしてきました。この実装は TC39 標準化プロセスよりも前のものでした。現在、デコレーターは [Stage 3 Proposal](https://github.com/tc39/proposal-decorators) であり、TS 5.0+ では特別な設定なしでサポートされています（https://github.com/microsoft/TypeScript/pull/52582 と https://devblogs.microsoft.com/typescript/announcing-typescript-5-0-beta/#decorators を参照）。

`experimental.decorators` を有効にすると、TypeScript の以前の `compilerOptions.experimentalDecorators` 実装では**なく**、TC39 提案のサポートが有効になります。

::warning
これが最終的に JS 標準に組み込まれる前に変更がある可能性があることに注意してください。
::

### 使用方法

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    decorators: true,
  },
})
```

```ts [app.vue]
function something (_method: () => unknown) {
  return () => 'decorated'
}

class SomeClass {
  @something
  public someMethod () {
    return 'initial'
  }
}

const value = new SomeClass().someMethod()
// これは 'decorated' を返します
```

## granularCachedData

`useAsyncData` と `useFetch` のデータ更新時（`watch`、`refreshNuxtData()`、または手動の `refresh()` 呼び出しによる）に `getCachedData` を呼び出してその結果を使用するかどうかです。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    granularCachedData: true
  }
})
```

::read-more{icon="i-simple-icons-github" color="gray" to="https://github.com/nuxt/nuxt/pull/31373" target="_blank"}
実装の詳細については PR #31373 を参照してください。
::

## pendingWhenIdle

`false` に設定すると、`useAsyncData`、`useFetch`、`useLazyAsyncData`、`useLazyFetch` から返される `pending` オブジェクトは、`status` も pending の場合にのみ `true` になる computed プロパティになります。

つまり、`immediate: false` が渡された場合、最初のリクエストが行われるまで `pending` は `false` になります。

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    pendingWhenIdle: false
  }
})
```
