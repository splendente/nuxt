この章の目標は、フレームワークの異なる部分、その実行順序、そしてそれらがどのように連携して動作するかの高レベルな概要を提供することです。

## サーバー

サーバーでは、アプリケーションへの初回リクエストごとに以下のステップが実行されます：

### ステップ 1: Nitro サーバーと Nitro プラグインのセットアップ（一度のみ）

Nuxt はモダンなサーバーエンジンである [Nitro](https://nitro.build/) によって動作しています。

Nitro が開始すると、`/server/plugins` ディレクトリ下のプラグインを初期化し実行します。これらのプラグインでは以下が可能です：
- アプリケーション全体のエラーをキャッチおよび処理。
- Nitro がシャットダウン時に実行されるフックの登録。
- レスポンスの変更などのリクエストライフサイクルイベント用フックの登録。

::callout{icon="i-lucide-lightbulb"}
Nitro プラグインはサーバー開始時に一度だけ実行されます。サーバーレス環境では、サーバーは各入力リクエストで起動し、Nitro プラグインも同様です。しかし、それらは待機されません。
::

:read-more{to="/docs/guide/directory-structure/server#server-plugins"}

### ステップ 2: Nitro サーバーミドルウェア

Nitro サーバーの初期化後、`server/middleware/` 下のミドルウェアがすべてのリクエストに対して実行されます。ミドルウェアは認証、ログ記録、リクエスト変換などのタスクに使用できます。

::warning
ミドルウェアから値を返すとリクエストが終了し、返された値がレスポンスとして送信されます。適切なリクエスト処理を確実にするため、この動作は一般的に避けるべきです！
::

:read-more{to="/docs/guide/directory-structure/server#server-middleware"}

### ステップ 3: Nuxt の初期化と Nuxt アプリプラグインの実行

Vue と Nuxt のインスタンスが最初に作成されます。その後、Nuxt はサーバープラグインを実行します。これには以下が含まれます：
- Vue Router や `unhead` などの組み込みプラグイン。
- `plugins/` ディレクトリに配置されたカスタムプラグイン。接尾辞なし（例：`myPlugin.ts`）や `.server` 接尾辞付き（例：`myServerPlugin.server.ts`）のものを含みます。

プラグインは特定の順序で実行され、互いに依存関係を持つ場合があります。実行順序や並行処理を含む詳細については、[プラグインドキュメント](/docs/guide/directory-structure/plugins)を参照してください。

::callout{icon="i-lucide-lightbulb"}
After this step, Nuxt calls the [`app:created`](/docs/api/advanced/hooks#app-hooks-runtime) hook, which can be used to execute additional logic.
::

:read-more{to="/docs/guide/directory-structure/plugins"}

### ステップ 4: ルート検証

プラグインの初期化後、ミドルウェアの実行前に、Nuxt は `definePageMeta` 関数で定義されている場合、`validate` メソッドを呼び出します。`validate` メソッドは同期または非同期にでき、動的ルートパラメータの検証によく使用されます。

- `validate` 関数はパラメータが有効な場合に `true` を返す必要があります。
- 検証が失敗した場合は、`false` または `statusCode` や `statusMessage` を含むオブジェクトを返してリクエストを終了させる必要があります。

詳細については、[ルート検証ドキュメント](/docs/getting-started/routing#route-validation)を参照してください。

:read-more{to="/docs/getting-started/routing#route-validation"}

### ステップ 5: Nuxt アプリミドルウェアの実行

ミドルウェアは特定のルートにナビゲートする前にコードを実行することを可能にします。認証、リダイレクト、ログ記録などのタスクによく使用されます。

Nuxt には 3 種類のミドルウェアがあります：
- **グローバルルートミドルウェア**
- **名前付きルートミドルウェア**
- **匿名（またはインライン）ルートミドルウェア**

Nuxt はアプリケーションへの初回アクセス時とルートナビゲーションのたびにグローバルミドルウェアを自動的に実行します。名前付きおよび匿名ミドルウェアは、対応するページコンポーネントで定義されたページ（ルート）メタの middleware プロパティで指定されたルートでのみ実行されます。

各タイプの詳細と例については、[ミドルウェアドキュメント](/docs/guide/directory-structure/middleware)を参照してください。

サーバーでのリダイレクトは `Location:` ヘッダーがブラウザーに送信されることになり、ブラウザーはこの新しい場所に新たなリクエストを行います。この時、クッキーに永続化されていない限り、すべてのアプリケーション状態がリセットされます。

:read-more{to="/docs/guide/directory-structure/middleware"}

### ステップ 6: ページとコンポーネントのレンダリング

Nuxt はこのステップでページとそのコンポーネントをレンダリングし、`useFetch` や `useAsyncData` で必要なデータを取得します。サーバーでは動的な更新や DOM 操作が行われないため、`onBeforeMount`、`onMounted`、それ以降のフックなどの Vue ライフサイクルフックは SSR 中に**実行されません**。

デフォルトで、Vue はより優れたパフォーマンスのために SSR 中の依存関係追跡を一時停止します。

::callout{icon="i-lucide-lightbulb"}
Vue SSR はアプリをトップダウンで静的 HTML としてレンダリングするため、すでにレンダリングされたコンテンツを戻って変更することが不可能なため、サーバーサイドにはリアクティビティがありません。
::

::important
`<script setup>` のルートスコープでクリーンアップが必要な副作用を生じるコードは避けるべきです。そのような副作用の例として、`setInterval` でタイマーを設定することがあります。クライアントサイドのみのコードでは、タイマーを設定し、`onBeforeUnmount` や `onUnmounted` でそれを破棄するかもしれません。しかし、SSR 中にはアンマウントフックが呼び出されることはないため、タイマーは永続したままになります。これを避けるために、副作用のあるコードを代わりに `onMounted` に移動してください。
::

::tip{icon="i-lucide-video" to="https://youtu.be/dZSNW07sO-A" target="_blank"}
Daniel Roe がサーバーレンダリングとグローバル状態について説明している動画を見る。
::

### ステップ 7: HTML 出力の生成

必要なすべてのデータが取得され、コンポーネントがレンダリングされた後、Nuxt はレンダリングされたコンポーネントと `unhead` の設定を組み合わせて、完全な HTML ドキュメントを生成します。この HTML は関連データとともにクライアントに送り返され、SSR プロセスを完了します。

::callout{icon="i-lucide-lightbulb"}
Vue アプリケーションを HTML にレンダリングした後、Nuxt は [`app:rendered`](/docs/api/advanced/hooks#app-hooks-runtime) フックを呼び出します。
::

::callout{icon="i-lucide-lightbulb"}
HTML を最終化して送信する前に、Nitro は [`render:html`](/docs/api/advanced/hooks#nitro-app-hooks-runtime-server-side) フックを呼び出します。このフックでは、追加スクリプトの注入やメタタグの変更など、生成された HTML を操作することができます。
::

## クライアント（ブラウザー）

ライフサイクルのこの部分は、選択した Nuxt モードに関係なく、ブラウザーで完全に実行されます。

### ステップ 1: Nuxt の初期化と Nuxt アプリプラグインの実行

このステップはサーバーサイドの実行と似ており、組み込みとカスタムの両方のプラグインが含まれます。

`plugins/` ディレクトリ内のカスタムプラグイン（接尾辞なし（例：`myPlugin.ts`）や `.client` 接尾辞付き（例：`myClientPlugin.client.ts`））がクライアントサイドで実行されます。

::callout{icon="i-lucide-lightbulb"}
After this step, Nuxt calls the [`app:created`](/docs/api/advanced/hooks#app-hooks-runtime) hook, which can be used to execute additional logic.
::

:read-more{to="/docs/guide/directory-structure/plugins"}

### ステップ 2: ルート検証

このステップはサーバーサイドの実行と同じで、`definePageMeta` 関数で定義されている場合は `validate` メソッドが含まれます。

### ステップ 3: Nuxt アプリミドルウェアの実行

Nuxt ミドルウェアはサーバーとクライアントの両方で実行されます。特定の環境で特定のコードを実行したい場合は、クライアントには `import.meta.client`、サーバーには `import.meta.server` を使用して分割することを検討してください。

:read-more{to="/docs/guide/directory-structure/middleware#when-middleware-runs"}

### ステップ 4: Vue アプリケーションのマウントとハイドレーション

`app.mount('#__nuxt')` を呼び出すことで、Vue アプリケーションが DOM にマウントされます。アプリケーションが SSR または SSG モードを使用している場合、Vue はクライアントサイドアプリケーションをインタラクティブにするためにハイドレーションステップを実行します。ハイドレーション中、Vue はアプリケーションを再作成し（[サーバーコンポーネント](/docs/guide/directory-structure/components#server-components)を除く）、各コンポーネントを対応する DOM ノードにマッチングさせ、DOM イベントリスナーをアタッチします。

適切なハイドレーションを確実にするためには、サーバーとクライアント間のデータの一貫性を維持することが重要です。API リクエストには、`useAsyncData`、`useFetch`、またはその他の SSR フレンドリーなコンポーザブルの使用が推奨されます。これらのメソッドはサーバーサイドで取得されたデータがハイドレーション中に再利用され、繰り返しリクエストを避けることを保証します。新しいリクエストはハイドレーション後にのみトリガーされ、ハイドレーションエラーを防ぐ必要があります。

::callout{icon="i-lucide-lightbulb"}
Vue アプリケーションのマウント前に、Nuxt は [`app:beforeMount`](/docs/api/advanced/hooks#app-hooks-runtime) フックを呼び出します。
::

::callout{icon="i-lucide-lightbulb"}
Vue アプリケーションのマウント後に、Nuxt は [`app:mounted`](/docs/api/advanced/hooks#app-hooks-runtime) フックを呼び出します。
::

### ステップ 5: Vue ライフサイクル

サーバーとは異なり、ブラウザーは完全な [Vue ライフサイクル](https://vuejs.org/guide/essentials/lifecycle)を実行します。
